# 제안: holdings 원장 체크포인트 — 시점이 섞인 복원을 PASS로 받지 않는다 (DRAFT)

**상태:** DRAFT 2026-10-09 — H6d-min(#1205)의 원장과 상태 파일이 서로 다른 시점에서 복원되면 기록이 조용히 사라지고 readiness는 PASS로 남는다(C7). 원장 사슬·체크포인트·이력 완전성을 세 검사로 나누고, 축소·교체는 거부하며 Thomas에게 알리고, 이력은 재수집 증거로만 복구로 판정하는 설계다(3차 검토, 같은 날). 회귀 테스트(`tests/test_mvp_runtime_holdings_c7_partial_restore.py`)가 오늘의 결함을 고정한다. 구현은 §10의 다섯 PR로, §12의 Thomas 결정 뒤에 한다.

> 이 문서는 아무것도 바꾸지 않는다. 운영 상태 파일에 체크포인트를 쓰거나 이전하지 않는다.
> 사실 확인 기준: `origin/main` = `3bbbe04d` (2026-10-09), 운영 `candidate-1205`. 코드 인용은 그 트리다.
> 거래소 사실은 Binance 개발자 문서(2026-10-09 열람)에서 가져왔다. 링크는 §4에 있다.

## 1. 문제

H6d-min에서 원장이 권위이고, 상태 파일은 캐시다. 그런데 상태 파일에는 원장에서 다시 만들 수 없는 것이 있다.
- 바이낸스 출처별 읽기 커서. 다음 fire는 `커서 − 1일`부터 읽는다.
- Toss의 직전 스냅샷. 다음 창은 이것과 현재를 비교한다.

| 경우 | 오늘의 결과 | 테스트 |
|---|---|---|
| 원장만 옛 백업, 커서는 겹침(1일) 안 | 다시 읽어 복구 | `test_c7_4_…within_the_overlap…` |
| 원장만 옛 백업, 커서는 3일 앞 | **기록 유실, 예외 1→0, readiness PASS** | `test_defect_c7_4_…` |
| 같은 줄 수, 다른 이력의 원장 | **진짜 기록 유실, 없는 기록 잔존, PASS** | `test_defect_c7_6_…` |
| 체크포인트 없는 상태(오늘의 모든 상태) | 관계를 확인할 수 없는데 PASS | `test_defect_c7_8_…` |
| 상태 파일 누락, 원장 끝이 8일보다 오래됨 | **기록 유실, PASS** | `test_defect_c7_11_…` |
| 원장 사슬 손상으로 모든 쓰기 거부 | **어떤 메시지도 나가지 않음** | `test_defect_c7_d_…` |

**원인 두 가지.**
1. `ledger_state_consistency`는 상태가 **어느 원장을 보고** 저장됐는지 보지 않는다.
2. 예외 알림은 원장을 먼저 검증하는 `summary()` 뒤에 계산된다(`store.refresh`). 원장이 깨지면 블록 전체가 예외로 끝나고, board에는 예외 클래스 이름만 남는다(reason_code 없음).

**커서는 감지 수단이 아니다.** 행이 없는 fire도 커서를 `now`로 옮긴다(`test_c7_7_…`).

## 2. 세 검사의 분리 (C7-A)

| 검사 | 무엇을 증명하나 | 증명하지 않는 것 | readiness |
|---|---|---|---|
| `ledger_chain` (기존) | 원장 각 줄이 앞 줄 해시를 품고 그대로다. | 줄이 빠졌는지, 다른 이력인지 | 기존 그대로 |
| 체크포인트 = 기존 `ledger_state_consistency`의 확장 | 지금 원장이, 상태가 마지막으로 본 원장(N줄, N번째 해시)의 **연장**이다. | 그 이전 이력이 거래소와 맞는지 | FAIL / PASS |
| `history_completeness` (새 검사 키 1개) | cutover 이후 이력이 재수집 증거로 맞춰졌다. | — | PASS / UNCHECKED / FAIL |

- **체크포인트를 처음 만드는 일**(체크포인트 없는 상태의 첫 쓰기)은 "그 시점의 원장을 관찰했다"는 사실만 증명한다. 이력 완전성은 `UNVERIFIED`로 시작한다.
- **체크포인트 검사를 따로 이름 붙이지 않는다.** 그것이 바로 "상태와 원장의 일관성"이다. 이름을 바꾸면 board와 Hermes가 보는 이름이 바뀐다.
- **`history_completeness`는 별도 키로 둔다.** 의미가 다르기 때문이다. 한쪽은 지금 원장이 기록과 맞는지, 다른 쪽은 과거가 거래소와 맞는지다. Registry·Gate가 아니라 readiness 안의 검사 하나다. 합칠지는 §12 D2에서 정한다.

**어휘 매핑(새 readiness 값은 없다).**

| 과제 용어 | 출처별 판정(평가 줄·board 상세) | `history_completeness` |
|---|---|---|
| BINANCE_RECOVERED | `binance: RECOVERED` | — |
| BINANCE_INCOMPLETE | `binance: INCOMPLETE` | — |
| (해당 없음) | `binance: UNVERIFIED` | — |
| TOSS_UNVERIFIED | `toss: UNVERIFIED` (빈틈 증거 있음 또는 연속성 미확인) | — |
| (해당 없음) | `toss: CONTINUOUS` (창이 cutover부터 빈틈없이 이어짐) | — |
| HISTORY_RECOVERED | binance RECOVERED **이고** toss CONTINUOUS | PASS |
| HISTORY_INCOMPLETE | 그 밖에 일부라도 복구됨 | UNCHECKED |
| HISTORY_UNVERIFIED | 증거 없음 | UNCHECKED |
| BLOCKED | 축소·교체·told 키 유실 | `ledger_state_consistency` FAIL |

**바이낸스 복구만으로 전체 이력 복구를 선언하지 않는다.** Toss는 재수집할 수 없으므로 "복구"가 없다. Toss는 연속성(CONTINUOUS)만 증명할 수 있다.

## 3. 감지 규칙 (C7-B)

- `_commit`의 `build` 안, 즉 상태 잠금과 원장 잠금 아래에서 판정한다.
  - 원장이 N줄 이상이고 N번째 해시가 같으면 정상이다. 사슬 때문에 1…N 전체가 같다.
  - 그렇지 않으면 `LEDGER_TAMPERED`를 던진다. legacy 거부와 같은 모양이라 아무것도 쓰이지 않는다.
  - 저장할 때 체크포인트를 새 끝으로 옮긴다.
- **둘째 감지기:** 상태의 `exceptions.told_keys`(알린 예외 키의 다이제스트) 가운데 원장의 어떤 예외 키와도 맞지 않는 것이 있으면, 유실이 증명된 것이다. 같은 거부로 처리한다.
- **체크포인트가 없으면** 쓰기를 막지 않는다. 막으면 더 잃는다. 관찰한 끝을 기록하고, 이력은 UNVERIFIED로 둔다.
- **readiness는 상태를 먼저, 원장을 나중에 읽는다.** readiness는 잠금 밖에서 계산된다(`update_readiness`도 잠금 전에 부른다). 반대 순서면 경합 때 오탐 FAIL이 난다.
- 원장 쓰기는 모두 `_commit`을 지난다. `_append`는 호출하는 곳이 없다.
- 롤백한 옛 코드는 상태 dict를 통째로 저장하므로 체크포인트 키를 보존하지만 옮기지는 않는다. 쓰기 함수들이 읽고 통째로 저장하는 패턴만 확인했다.

| 상황 | 판정 | 테스트 |
|---|---|---|
| 정상 원장 연장 | 정상 | C7-1, C7-3 |
| append 뒤 저장 전 중단 | 체크포인트가 뒤처진 조상 → 정상 | C7-2 |
| 상태 캐시만 이전 버전 | 조상 → 정상, 옛 커서가 다시 읽음 | C7-3, C7-10 |
| 원장만 이전 버전 | 축소 → BLOCKED | C7-4 |
| 같은 길이의 다른 원장 | N번째 해시 다름 → BLOCKED | C7-6 |
| 체크포인트 없는 기존 상태 | 쓰기 허용, 관찰 기록, 이력 UNVERIFIED | C7-8 |
| 상태 파일 누락 | 같음. 단 §5의 자동 재수집으로 RECOVERED 가능 | C7-11 |
| 원장 사슬 손상 | 기존 `LEDGER_TAMPERED` | C7-9 |

**정상 복구 경로 중 바뀌는 하나.** C7-4에서 원장만 이전 버전이고 커서가 겹침 안인 경우는 오늘 자동으로 복구된다. 설계는 이것도 BLOCKED로 본다. 원장 축소는 복원 말고는 생기지 않기 때문이다. 대가는 운영자 채택 1회다(§12 D1).

## 4. 거래소 응답의 완전성 (C7-C)

| 출처 | 페이지 인자 | 기본 / 최대 | `total` | 문서 |
|---|---|---|---|---|
| `crypto_deposit` | `limit`, `offset` | 1000 / 1000 | 없음 | [deposit history](https://developers.binance.com/docs/wallet/capital/deposite-history) |
| `crypto_withdraw` | `limit`, `offset` | 1000 / 1000 | 없음 | [withdraw history](https://developers.binance.com/docs/wallet/capital/withdraw-history) |
| `fiat_deposit`·`fiat_withdraw`·`fiat_buy`·`fiat_sell` | `page`, `rows` | 100 / 500 | 있음 | [fiat history](https://developers.binance.com/docs/fiat/rest-api/Get-Fiat-Deposit-Withdraw-History) |
| `pay` | `limit` | 100 / 100 | 없음, 페이지 없음 | [pay history](https://developers.binance.com/docs/pay/rest-api/Get-Pay-Trade-History) |
| `transfer_spot_to_futures`·`transfer_futures_to_spot` | `current`, `size` | **10** / 100 | 있음 | [universal transfer](https://developers.binance.com/docs/wallet/asset/query-user-universal-transfer) |

**오늘의 코드.** `binance_wallet.flow_history`는 페이지 인자를 보내지 않고 `total`도 보지 않는다. 따라서 **이체는 읽기 창 하나에 10건, Pay와 fiat은 100건을 넘으면 말없이 잘린다.** 커서는 그대로 `now`로 간다.
- 정상 운영의 읽기 창은 약 1일 + 겹침이다. 첫 읽기는 7일이다.
- 문서는 응답 순서를 밝히지 않는다. 그래서 잘릴 때 어느 쪽 행이 빠지는지는 **미확인**이다.
- 운영에서 실제로 잘린 적이 있는지는 원장을 읽어야 알 수 있어 이 문서에서 확인하지 않았다(**미확인**).
- C7과 별개로 운영에 있던 결함이다. **PR-0으로 지어졌다: #1210**(2026-10-10 머지, 같은 날 10:13Z 배포). 이 절의 "오늘의 코드"는 #1210 이전의 `main`이다. #1210은 다음을 더했다.
  - 출처별 페이지 크기를 명시하고, 가득 찬 페이지는 시간으로 나눠 다시 읽는다.
  - `total`이 있는 출처는 그것을 필수로 대조한다.
  - 객체가 아닌 행이 오면 거부한다.
  - 요청 창을 양쪽으로 한 순간씩 넓혀 첫·끝 순간의 행을 받는다.
  - ID 없는 행은 내용으로 합치지 않는다.
  - fiat·Pay의 실패 본문(`code`/`success`)을 거부한다.
  - 완전성을 보일 수 없으면 그 출처가 실패하고 커서를 유지한다.
  - 실제 응답 계약(`total`의 뜻, 본문 필드의 존재, 경계 포함 여부, 정렬)은 NOT_VERIFIED다.
- §5의 RECOVERED 증거 1–3(창, PASS, 끝까지 읽기)은 #1210의 한 번 읽기 수준에서 갖춰진다. 4(원장에만 있는 기록 대조)와 재수집 판정 줄은 여전히 PR-B 범위다.

**RECOVERED의 증거(출처마다 모두):**
1. 읽기 창이 `cutover − 1일`까지 닿는다. 조회 한도는 이체 7일, 그 밖 89일이다(코드의 `FLOW_SOURCES` 값).
2. 모든 요청이 PASS다.
3. 페이지를 끝까지 읽었다.
   - `total`이 있는 출처는 받은 행 수가 `total`과 같다.
   - `total`이 없는 출처는 마지막 페이지가 최대보다 작다.
   - Pay는 페이지가 없으므로, 100건이 오면 창을 반으로 나눠 다시 읽는다.
4. 재수집 창 안의 원장 기록이 모두 거래소 응답에 있다.

그 밖의 처리는 다음과 같다.
- 중복은 `append_unique`가 키로 막는다.
- 잘린 응답은 그 출처의 읽기 실패로 거부하고 커서를 옮기지 않는다.
- **원장에만 있는 기록**(거래소가 돌려주지 않는 기록)은 원장이 append-only라 지울 수 없다. 그런 기록이 있으면 그 출처는 RECOVERED가 아니다. Thomas가 기존 해소 종류 `acknowledged_excluded`로 정리해도 판정은 오르지 않는다. 그 종류는 지금 중복·반전·형식 오류·보류에만 허용된다(`ALLOWED_KINDS`).
- **Toss의 과거 이력은 복구할 수 없다.** 과거 현금을 읽는 길이 없고, `collect_toss`는 상태의 직전 스냅샷과 현재를 비교할 뿐이다.
- **Toss 창은 정상 운영에서도 빈틈이 생긴다(코드 확인).** 이것이 설계의 열린 조건이다.
  - 스냅샷의 현금·환율이 비어 "사용 불가"인 fire는 창 줄을 쓰지 않는다. 원장에 더 새로운 창이 있는 경우도 쓰지 않는다. 두 경우 모두 `patch`가 상태의 `toss`를 현재로 옮긴다. 다음 창은 그 뒤에서 시작하므로 그 사이가 빈다.
  - Toss 통과 전체가 실패하면 직전 시점이 그대로라 다음 창이 그 구간을 덮는다.
  - 결과적으로 "창이 빈틈없이 이어짐"으로는 유실과 정상적인 빈틈을 가를 수 없다. 이대로면 `toss: CONTINUOUS`를 만들 수 없고 `history_completeness`는 PASS에 닿지 못한다.
  - **선택지(§12 D2):**
    - (a) 건너뛴 창을 원장 줄(`toss_window_skipped`, 이유 포함)로 남겨 빈틈마다 설명이 붙게 한다. 런타임 추가이며 PR-B 범위다. 그 이전 구간은 설명이 없으므로, 그 구간에 빈틈이 하나라도 있으면 Toss는 UNVERIFIED다. 운영 원장에 빈틈이 있는지는 LOCAL_ONLY라 이 문서에서 확인하지 못했다.
    - (b) Toss 판정을 체크포인트가 생긴 뒤 구간으로 한정한다. 그 이전은 cutover를 옮겨 새로 시작한다. 이 경우 shadow 관찰이 다시 시작된다.
    - 권장: (a).

**판정에서 벗어나는 길.** UNVERIFIED나 INCOMPLETE는 시간이 지나거나 Thomas가 승인해도 PASS가 되지 않는다. 기존 `set_cutover`로 빈 구간 뒤에 cutover를 옮기면 관찰이 그때부터 다시 시작한다.

## 5. 재수집 판정 (상태 누락, 첫 이전, 채택 뒤 공통)

- 출처마다 `max(cutover − 1일, now − 조회 한도)`부터 다시 읽는다.
- 결과는 원장 줄 하나(`history_assessed`)로 남긴다. 담는 것: 출처별 창, 읽은 페이지 수, 행 수, `total`, 잘림 여부, 원장에만 있는 기록 수, 판정. 금액은 담지 않는다.
- 상태 파일 누락(C2)은 다음 fire가 커서 없이 약 8일 전부터 읽으므로 이 판정이 자동으로 한 번 돈다. 증거가 갖춰지면 RECOVERED, 아니면 UNVERIFIED다.
- **운영 첫 이전:** cutover가 7일보다 오래됐으면 이체 출처 때문에 INCOMPLETE에서 출발한다. 운영 cutover 시각은 board에 나오지 않아 **미확인**이다.

## 6. BLOCKED 알림 (C7-D)

**경로.** 원장 쓰기가 막혀도 동작해야 하므로 `summary()`와 예외 알림 블록 **밖**에 둔다. `store.refresh`가 현금흐름 단계의 `ToolError`를 잡는 자리에서 reason_code를 그대로 보존한다. 오늘은 클래스 이름만 남는다.

| 요구 | 설계 |
|---|---|
| 원장 쓰기 실패 시에도 알림 | 원장과 상태 어느 쪽도 쓰지 않는다. told 표시는 낙폭 told 표시(`combined.write_told`)와 같은 형식의 별도 작은 파일에 원자적으로 쓴다. |

| 재시작 뒤 유지 | told 파일은 디스크에 있다. 처음 본 시각과 **그때의 원장 끝 시각**도 그 파일에 둔다. |

| 시작 시각과 reason_code | 위 told 파일의 처음 본 시각과 장애 키의 reason_code |
| 조회 한도 초과 위험 | 남은 날 = (**처음 감지 때 기록한** 원장 끝 시각 + 7일) − 지금. 이체가 가장 짧다. 지금의 원장 끝을 쓰면 감지만 하는 단계에서 마감일이 계속 뒤로 밀려 진짜 마감을 가린다. 0 이하이면 "이체 기록은 이미 재수집 한도 밖"이라고 알린다. |

- **대상:** `LEDGER_TAMPERED` 계열만 BLOCKED로 본다(사슬, 상태 판독 불가, 체크포인트, legacy 거부). 잠금 시간 초과(`*_LOCKED`)는 일시적이므로 대상이 아니다.
- **장애가 풀리면:** 장애 키가 사라진다. 해소 문구 1회를 보낼지는 §12 D1에서 정한다.
- **scheduler 자체 정지:** 이 경로로 잡을 수 없다. 별도 외부 감시가 맡는다(범위 밖).
- **재사용 경계:** 기존 H6d 예외 알림(`exceptions_token`)은 원장이 읽혀야 계산되므로 BLOCKED에 쓸 수 없다. 재사용하는 것은 낙폭 told 파일의 형식과 "전달 뒤 표시" 방식이다.

## 7. 운영자 채택 (C7-E)

`holdings_board --adopt-ledger`는 일반 쓰기가 아니다. 일반 쓰기가 막힌 상태에서 감사 기록을 남기는 유일한 길이다.

1. **명시적 승인:** 대화형 터미널에서만 받는다. `--by`와 `--reason`이 필수다. scheduler·Hermes 문에서는 거부한다. 기존 `start_semantics_epoch`·`resolve`와 같은 조건이다.
2. **두 단계 확인:** 첫 실행은 쓰지 않는다. 지금 원장 끝(줄 수, 해시 앞 8자리)과 상태의 체크포인트, 감지 사유를 보여 준다. Thomas가 `--confirm <해시 8자리>`로 다시 실행한다. 기존 epoch 확인(`confirm=digest[:8]`)과 같은 모양이다.
3. **쓰기 직전 재확인:** 두 잠금 아래에서 사슬을 다시 검증하고, 끝이 확인한 해시와 같은지 본다. 다르면 거부한다. 확인과 쓰기 사이에 원장이 바뀐 경우다.
4. **권한 경계:** 체크포인트 검사를 건너뛰는 것은 이 명령의 자기 줄 하나뿐이다. 일반 `_commit` 경로는 그대로 거부한다.
5. **멱등:** 키는 `ledger_adopted:<확인한 끝 해시>`다. 같은 끝에 다시 실행하면 줄이 늘지 않는다.
6. **중단 후 재실행:** 채택 줄이 쓰였는데 상태가 저장되지 않았으면, 다음 쓰기는 이렇게 판단한다. "상태의 체크포인트 = 채택 줄이 기록한 덮어쓴 체크포인트"이고 원장이 채택 줄의 연장이면 정상으로 이어간다.
7. **감사:** 채택 줄에는 덮어쓴 체크포인트, 채택한 끝, 요청자, 이유, 시각이 담긴다. append-only이고 **어떤 기록도 지우지 않는다.**
8. **채택은 `history_completeness`를 바꾸지 않는다.** 채택 뒤 §5의 재수집이 돌고, 그 증거만이 판정을 올린다.

## 8. 영향 범위

- **NAV·낙폭:** 영향 없다. `combined.py`는 `cash_flows`를 import하지 않는다.
- **readiness:** UNCHECKED·FAIL이면 `ready=False`이고 `H6b_shadow_ready` 알림이 나가지 않는다. 운영은 지금도 `ready=False`다.
- **shadow 관찰:** UNCHECKED에서도 쌓인다(`mark_fire_verified`는 바이낸스·Toss 성공에 달렸다). BLOCKED에서는 쌓이지 않는다.
- **재시작:** 판정이 원장 줄에 있으므로 유지된다.

## 11. 백업 담당 세션에 넘길 요구사항

1. **원장과 상태의 일관된 스냅샷:** 잠금 아래에서 두 파일만 스테이징으로 복사하고, 잠금을 푼 뒤 tar한다.
2. **잠금:** holdings 현금흐름 **상태 잠금 하나**(`*.lock` 사이드카, `fcntl.flock`, `filelock.locked`와 같은 파일)를 잡는다. H6d-min 이후 모든 쓰기가 상태 → 원장 순서이므로 이것으로 쓰기가 배제된다. 원장 잠금은 잡지 않는다(순서 역전 방지).
3. **호스트·컨테이너 flock 호환:** 서비스는 uid 10001, 백업은 root다. bind mount로 같은 inode의 flock이 공유되는지 합성 디렉터리에서 먼저 시험한다(**미확인**).
4. **잠금 시간과 scheduler 영향:** 파일 두 개 복사, 밀리초 단위다. 쓰기 쪽은 최대 60초(`ACQUIRE_DEADLINE_SECONDS`) 기다린 뒤 `STATE_LOCKED`로 실패하고 커서를 유지한다. 백업(07:45Z)과 fire(:34)는 시간대가 다르다.
5. **암호화 백업 복원 검증:** 맥에서 복호화해 임시 디렉터리에 해제한 뒤, 사슬과 체크포인트 관계를 검증한다. 상태 단어만 출력하는 읽기 전용 검증 명령이 필요하다. PR-A에 포함할 것을 제안한다. 실제 복원은 지금까지 시험한 적이 없다.
6. **체크포인트 검증:** 복원 전에 상태의 체크포인트가 해제된 원장의 조상인지 본다. 아니면 복원하지 않거나, 복원 뒤 BLOCKED와 채택을 예상한다.
7. **나머지 holdings 파일은 별개다.** 기준선 로그는 자체 잠금이 있는 사슬이고, 고점·told 파일은 잠금 없이 쓰인다. **두 파일 잠금은 holdings 디렉터리 전체의 시점 일관성을 보장하지 않는다.** 고점과 told가 다른 시점이면 #1206이 다룬 종류의 판정 어긋남이 생길 수 있다.
8. **H6b 이미지로 롤백한 동안:** H6b 코드는 상태 잠금을 잡지 않는다. 이 동안 스냅샷 잠금은 쓰기를 배제하지 못한다.

**복원 후 점검** (`holdings_board --json`):
- `ledger_chain` PASS.
- `ledger_state_consistency` PASS(FAIL이면 BLOCKED, 채택 결정).
- `history_completeness` 값.
- cutover가 복원 전 값과 같다.
- 미해결 예외 수가 줄지 않았다.
- 중복 키가 없다.
- `combined.portfolio_nav_complete`가 true다.
- 실행 단계가 PAPER다.

확인하지 못한 항목이 있으면 PASS로 보고하지 않는다.

**롤백(H6b 코드)과의 관계:**
- 롤백 기간에 상태에만 쌓인 Toss 증거는 재전진 때 가져오지 않는다.
- 예외 알림이 1회 중복된다(`told_count` 미갱신).
