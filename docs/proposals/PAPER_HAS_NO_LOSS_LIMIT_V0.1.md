# 제안: 페이퍼에는 손실한도가 없어야 한다 — C4 판정을 둘로 가른다 (DRAFT v0.1)

**상태:** DRAFT — 설계 선행(구현 아님). 코드 변경 없음.
**근거:** `crypto/cycle.py`(사이클 판정 배선), `crypto/guards.py`(C4 브레이커),
`crypto/lifecycle.py`(강등 사다리), `crypto/counterfactual.py`(그림자 등록부),
`crypto/live_route.py`·`live_entry.py`(라이브 문).
**측정 시점:** 2026-07-31 10:20 UTC, `thomas-scheduler`, 읽기 전용.
**관계:** #400(Gate 0 배선)이 이 설계에서 **하중을 받는 부재**가 된다. #405(드로다운 재기준화)는
이 결정이 채택되면 범위가 라이브 전용으로 좁아지거나 불필요해진다.
**결정 요청:** §7.

---

## 0. 한 줄

손실한도는 **돈을 잃지 않기 위해** 존재한다. 페이퍼는 돈을 잃지 않는다. 페이퍼에 손실한도를
걸어서 실제로 일어난 일은 손실 방지가 아니라 — **자신을 풀어줄 증거의 생산 중단**이었다.

## 1. 측정 — 브레이커가 막은 것이 실제 거래의 7.6배다

| | |
|---|---|
| 실제 페이퍼 결과 (자체) | **86건** |
| 브레이커가 막아 그림자로만 남은 것 | **656건** |
| 그림자 총합 | -249.63R (총액 기준) |

차단 사유(중복 포함): 연속손실 394 · 주간 393 · 일간 320 · 드로다운 49.

## 2. 교착의 진짜 모양

2026-07-31에 라우팅 중이던 5개 전략의 거래 수는 2, 3, 3, 9, 13건이었다. `lifecycle`의 창은
warn 20 / probation 30 / suspend 50이다. **다섯 전략 모두 가장 낮은 창에도 닿지 못했다** — 즉
사다리는 이들을 강등할 수단이 구조적으로 없었다.

왜 표본이 얇았는가. 브레이커가 막았기 때문이다. 그리고 브레이커는 왜 걸렸는가. 그 전략들이
졌기 때문이다. 그래서:

```
브레이커 걸림 → 신규 진입 차단 → 표본 안 쌓임 → 사다리가 강등 못 함
      ↑                                                    │
      └──────── 지는 전략이 라우팅에 그대로 남음 ←─────────┘
```

**손실한도가 자신을 해제해줄 증거를 스스로 차단하는 순환**이다. 656건이 실제로 정산됐다면 다섯
전략 모두 suspend 창(50)을 넘겼을 것이고, 사다리가 진작 처리했을 것이다.

## 3. 제안 — 판정을 둘로 가른다

`cycle.py`는 지금 C4 판정을 **하나** 만들어 페이퍼와 라이브 양쪽에 먹인다. 그것을 가른다.

| | 페이퍼 | 라이브 |
|---|---|---|
| 손실 브레이커(일간·주간·연속·드로다운) | **없음** | **강제**, 라이브 결과 위에서 계산 |
| 나쁜 전략을 걸러내는 수단 | `lifecycle` 사다리 | 사다리 + 브레이커 |
| 포지션 한도·`MAX_ENTRY_COST_R` | 그대로 | 그대로 |
| 진입 자격 | — | **Gate 0** (#400): 페이퍼 실적이 순 기준 양의 기대값 |

**두 층으로 나뉜다:** 페이퍼 증거가 *라이브를 시작해도 되는가*를 결정하고, 라이브 결과가
*라이브를 계속해도 되는가*를 결정한다. 지금은 이 두 질문을 병합된 브레이커 하나가 동시에,
그리고 잘못 답하고 있다.

### 3.1 강등은 사다리의 일이지 브레이커의 일이 아니다

브레이커는 포트폴리오 수준의 제동이고, 사다리는 전략 수준의 판단이다. "이 전략이 나쁜가"에
답해야 할 때 브레이커를 쓰면 **좋은 전략까지 같이 멈춘다** — 그리고 나쁜 전략을 식별할 표본이
사라진다. 페이퍼에서 필요한 것은 후자다.

### 3.2 그림자를 뒤집는다

지금 `counterfactual`은 *막힌 거래*를 기록한다 — 실제 결과 대신 가상 결과가 남는다. 이것을
뒤집는다: **페이퍼는 실제로 거래하고, "라이브였다면 여기서 막혔다"를 기록한다.**

같은 모듈, 같은 등록부, 입력만 반대다. 그리고 결과가 낫다 — 실제 결과 **와** 브레이크의 가상
효과를 둘 다 얻는다. 지금은 가상 결과만 얻는다.

### 3.3 천장은 유지된다 — 다만 무엇의 천장인지 분리한다

`cycle.py`는 *"a live entry can never be permitted where a paper one was not"* 를 보장한다. 이
보장은 두 개가 겹쳐 있다:

- **신호의 천장** — 라이브는 페이퍼 라우터가 제안한 것만 거래한다(`shared_route`). **유지한다.**
- **리스크 상태의 천장** — 라이브는 페이퍼의 C4 판정을 공유한다. **이것을 라이브 자신의
  브레이커로 옮긴다.**

전자가 "라이브가 페이퍼 밖의 일을 하지 않는다"를 지키는 부분이고, 후자는 페이퍼의 손실이
라이브를 막는 부분이다. 분리 대상은 후자뿐이다.

## 4. 무엇이 바뀌지 않는가

- **페이퍼가 무제한이 되지 않는다.** 포지션 한도(동시 20 / 심볼당 4 / 방향 스큐 4),
  `MAX_ENTRY_COST_R = 0.25`, 데이터 건전성 가드, 킬 스위치는 전부 그대로다. 사라지는 것은
  **손실** 브레이커뿐이다.
- **원장은 그대로다.** 과거 결과는 수정되지 않는다.
- **라이브는 더 느슨해지지 않는다.** 오히려 브레이커가 라이브 결과 위에서 계산되므로,
  페이퍼의 잡음이 아니라 실제 손실에 반응한다.
- **`live_readiness`, 예산 캡, 카나리아, 킬 스위치** 전부 불변.

## 5. 반대 논거

**(1) "페이퍼가 라이브를 예측하지 못하게 된다."** 가장 실질적인 반론이다. 라이브는 브레이크가
걸린 채 돌 텐데 페이퍼가 안 걸린 채 돌면 두 통계가 다른 시스템을 서술한다. §3.2가 답이다 —
브레이크의 효과를 페이퍼 쪽에 **기록**하면 두 버전(브레이크 있음/없음)을 모두 재구성할 수 있다.
지금은 브레이크 걸린 버전 하나만 있고, 그마저 표본이 86건이다.

**(2) "라이브 브레이커가 초기에 무력하다."** 라이브 결과가 0건이면 주간·드로다운·연속손실이
전부 0이다. `run_risk_guard`는 빈 목록을 *"아직 닫힌 거래가 없다"* 로 읽고 거래를 허용한다 —
읽을 수 없는 이력(`risk_guard_unreadable`, 거부)과 구분되는 기존 의미론 그대로다. 그리고 이
구간을 메우는 것이 **Gate 0**다: 페이퍼 실적이 순 기준 양의 기대값을 보이기 전에는 라이브 진입
자체가 없다. 이 설계에서 #400은 선택이 아니라 **필수 부재**가 된다.

**(3) "손실한도 제거는 리스크 확대다."** 페이퍼에서는 아니다. 확대되는 것은 거래 횟수이고,
비용은 거래소 읽기와 연산뿐이다. 그리고 그 거래가 만들어내는 것이 정확히 사다리와 Gate 0가
읽어야 하는 증거다.

**(4) "그림자 656건 합계가 -249.63R이니 브레이커가 지켜준 것 아닌가."** 페이퍼 돈은 돈이 아니다.
지켜준 것이 아니라 **656개의 데이터 포인트를 보류한 것**이고, 그 데이터가 있었다면 사다리가
해당 전략들을 훨씬 일찍 내렸을 것이다. 브레이커가 막아준 손실은 가상이고, 막아버린 증거는 실재다.

## 6. 남는 위험

- **판정이 하나에서 둘로 갈라진다.** 이 저장소가 반복해서 경계하는 "두 문이 서로 다른 답을 할
  수 있는" 구조다. 두 판정이 각자 무엇을 입력으로 받는지 코드가 한 곳에서 말해야 한다.
- **라이브 브레이커를 라이브 결과 위에서 새로 계산해야 한다.** 지금 라이브 전용인 것은 일간
  손실(거래소 실현손익)뿐이다. 주간·드로다운·연속손실은 만들어야 한다.
- **표본이 커지면 페이퍼가 더 자주 진다.** -249.63R이 원장에 실제로 들어오면 Gate 0는 더
  강하게 닫힌다. 그것이 옳은 동작이지만, 라이브 개시는 지금보다 **멀어진다.** 이 제안은 라이브를
  빨리 켜는 안이 아니라 정직하게 켜는 안이다.
- **`counterfactual` 등록부의 의미가 바뀐다.** 과거 656건과 이후 기록은 서로 다른 것을 뜻하게
  되므로, `r_basis`가 그랬듯 버전 표시가 필요하다.

## 7. 결정 요청

1. **페이퍼에서 손실 브레이커를 제거하는가?** (예 / 아니오)
2. **라이브 브레이커를 라이브 결과 위에서 별도 계산하는가?** (권고: 예)
3. **신호의 천장(`shared_route`)은 유지하는가?** (권고: 예 — 분리 대상은 리스크 상태뿐)
4. **`counterfactual`을 뒤집어 브레이크 효과를 기록하는가?** (권고: 예 — §5-(1)의 답)
5. **#405(드로다운 재기준화)를 라이브 전용으로 좁히거나 닫는가?**
6. **#400(Gate 0 배선)을 이 설계의 전제로 승격하는가?** (권고: 예 — §5-(2))

## 8. 이 제안이 하지 않는 것

- 코드를 바꾸지 않는다. 브레이커를 끄지 않는다.
- 포지션 한도·비용 게이트·킬 스위치·예산 캡을 건드리지 않는다.
- 라이브를 더 허용하지 않는다. 어떤 승인도 소비하지 않는다.
- 원장의 어떤 행도 수정하지 않는다.
