# 제안: 시스템 전수 점검 — 미흡·병목·개선 구간과 개선 설계 (DRAFT v0.1)

**상태:** DRAFT — 점검과 설계만 담았다. 코드 변경 없음, 정책 활성화 없음. §5의 결정 항목은 Thomas 결정 대기.
**점검 시각:** 2026-09-25, 브랜치 `claude/awesome-sagan-i59bu5` = main `083799c`(#978)과 같은 트리.
**점검 범위:** 코어 런타임(`runtime/mvp_runtime/` 중 crypto 제외), 크립토 레인(`crypto/`), 비크립토
제품 경로(분석·블로그·지식·Hermes), 개발 프로세스(CI·테스트·문서), 운영(백업·헬스체크·비밀).
**한계:** 라이브 호스트(`/root/thomas_agent`, 도커, `.runtime_governance_state/`)에는 접근하지 않았다.
운영 수치는 모두 문서에 기록된 값을 날짜와 함께 인용했고, 호스트에서 다시 재지 않았다. 라이브 돈 경로는
코드 읽기만 했고 실행하지 않았다(CLAUDE.md 가드레일).

검증 표기: **[확인]** = 코드·명령으로 직접 확인하거나 실측함. **[문서]** = 저장소 문서에 기록된 값(날짜 표기).
**[추정]** = 코드와 수치에서 추론했고 실측하지 않음.

## 0. 한 줄

**안전 규율은 튼튼하고, 약점은 그 바깥에 있다.** 라이브 경로에서 fail-open 경로는 찾지 못했고 테스트
8,954개도 건강하다. 문제는 네 곳에 있다.

1. **몇 달 뒤에 터질 코어의 신뢰성 시한폭탄.** 잠금에 타임아웃이 없고, 리스크 fire에 감시견이 없고,
   이력 전체를 매번 읽는 저장소들이 있다.
2. **품질이 측정되지 않는 분석 레인.** 페일오버 범위가 좁고, 근거 검증은 사실상 항상 통과하며,
   리스크 항목은 답변에서 빠진다.
3. **크립토 레인의 병목은 코드가 아닌데 개발 노력은 코드에 쏠려 있다.** 병목은 거래 빈도 × 달력
   시간, 그리고 비용 모델의 타당성이다.
4. **개발 프로세스 비용이 커졌다.** 중복 CI가 돌고, 충돌을 부르는 파일이 두 개 있고, 소유자가 5분
   안에 상태를 읽을 수 없다.

## 2. 발견 사항

심각도는 **높음/중간/낮음**이다. 노력은 **S**(PR 1개), **M**(PR 여러 개), **L**(구조 변경)이다.

### A. 코어 런타임 — 신뢰성과 확장성

**A1. POSIX 파일 잠금에 타임아웃이 없다.** 중간(영향 범위는 시스템 전체) · [확인]
- **근거.** `filelock.py:40`은 `fcntl.flock(LOCK_EX)`로 무기한 블로킹한다. 반면 모듈 docstring
  (`:12-13`)은 "멈춘 보유자는 거부로 바뀐다, 무한 대기는 없다"고 약속하며, 이 약속은 Windows 경로에만
  구현돼 있다. 운영 환경은 Linux다.
- **영향.** 컨테이너 8개가 records·audit·schedules·task registry 잠금을 공유하고, 잠금은 중첩된다
  (`consumption.py`: spend → approvals → working memory → audit). 보유자 하나가 멈추면 모든 컨테이너의
  모든 쓰기가 무기한 멈춘다. 겉으로 보이는 증상은 오래된 heartbeat 하나뿐이다.
- **설계.** `LOCK_NB`로 폴링하다 기한(예: 60초)을 넘기면 `PersistenceError(code)`를 낸다. docstring이
  이미 약속한 동작이다. 사이드카 파일에는 보유자 PID와 label을 기록한다.
- **주의(라이브 경로 인접).** 주문 직후의 감사 append(`live_route.py:1078-1084`)는 이미
  `MvpRuntimeError`를 잡아 `AUDIT_NOT_RECORDED`를 남기므로, 타임아웃이 `PersistenceError`(그 하위
  클래스)로 바뀌어도 이 지점은 처리된다 [확인]. 주문 **전**의 잠금(진입 claim, 주문 카운터, 브레이커
  상태)이 거부되면 진입도 거부되므로 fail-closed 방향이다. 확인이 남은 곳은 주문 **후** 정산 쓰기
  경로들이다. 기한은 충분히 길게(예: 60초) 잡고, 그 경로들을 Thomas가 검토한 뒤 머지한다. 노력 S.

**A2. 리스크 레인 fire에 벽시계 기한이 없다.** 중간
- **근거.** `run_due`(`scheduler.py:2575`)는 기한 없이 `_execute`를 호출한다. 기한이 있는 것은 factory
  자식(900초)과 워커 위임(900/1500초)뿐이다. urllib의 `timeout=`은 소켓 연산 하나를 제한할 뿐 전체
  시간은 제한하지 않고, DNS 조회도 덮지 않는다. heartbeat는 pass가 끝난 뒤에만 기록되고, compose는
  `unhealthy` 상태에서도 재시작하지 않는다. `health_watch.sh`는 10분 주기에 2회 연속을 요구하므로
  알림까지 약 25–30분이 걸린다. [확인]
- **영향.** `crypto_pipeline` fire 하나가 멈추면 같은 프로세스의 `crypto_breaker_watch`와
  `crypto_route_watch`도 함께 조용히 멈춘다. 거래소에 걸린 stop이 포지션은 지키지만, 정산·보유시간
  청산·경로 보고는 멈춘다. [추정]
- **설계.** 리스크 kind마다 감시 스레드를 둔다. 기한을 넘기면 `faulthandler.dump_traceback`,
  failed 이벤트 기록, `os._exit` 순으로 처리해 도커가 레인을 재시작하게 한다. fire 시작 시에는 "busy"
  heartbeat(kind와 기한 포함)를 먼저 찍어, 긴 유지보수 fire가 거짓 `unhealthy`로 보이는 문제(A9)도 함께
  없앤다. 리스크 heartbeat가 STALE이 되면 operator가 텔레그램 알림을 보낸다. 노력 M, 라이브 경로 인접.

**A3. programization 패턴 저장소가 실행 횟수의 제곱으로 커진다.** 중간 · 코드 [확인], 도달 시점 [추정]
- **근거.** 성공한 실행마다 관찰·패턴 파일 전체를 잠금 아래에서 읽고, 누적 `valid_observation_ids`
  목록 **전체**를 담은 새 패턴 행을 append한다(`programization.py:273-318`). 같은 행이 `records.jsonl`에도
  들어가 영구 보관된다.
- **실측.** 같은 패턴의 성공 실행이 500회면 파일 4.2 MB·실행당 25 ms, 2,000회면 65 MB·364 ms,
  5,000회면 402 MB·6.2초다. operator(512m)와 pipeline-worker(1g) 안에서는 결국 OOM이 되고, 그 뒤로는
  성공한 실행마다 실패한다.
- **도달 시점.** 분석 레인 사용량이 적어서 수개월~1년 이상 뒤다 [추정]. 고치는 비용이 가장 싼 지금이
  적기다.
- **설계.** 행에는 `count`와 이번 관찰 id(델타)만 담고, TRIGGERED 이후에는 id를 더 쌓지 않는다.
  `patterns.jsonl`은 id별 최신 행으로 압축한다. 닫힌 스키마를 올려야 하므로 스키마 버전 변경이
  필요하다. 노력 S–M.

**A4. task registry와 approval 저장소가 "최신 행 우선" append-only이고, 압축 없이 매번 전체를 읽는다.** 중간 · [확인]
- **실측.** 태스크 1만 개(16 MB)면 연산당 265 ms, 3만 개면 820 ms이고, 모두 잠금 아래에서 돈다.
  approvals 62 MB에서 `pending()`은 1.1초다. operator는 이 비용을 배치마다 낸다(`operator.py:1844,1916`).
  두 저장소 모두 `retention.ROTATABLE_FILES`에 없다.
- **부수 버그.** `enqueue`는 큐 깊이 확인(`task_registry.py:574`)과 제출(`:585`)을 서로 다른 잠금에서
  한다. 동시에 제출하면 `QUEUE_DEPTH_LIMIT`를 넘을 수 있다.
- **설계.** 최신 상태 스냅샷 사이드카를 두고, 스냅샷 이후 행만 적용한다. 종료된 항목은 retention과 같은
  방식으로 아카이브한다. 깊이 확인은 제출과 같은 잠금 안으로 옮긴다(이 부분만 S). 노력 M.

**A5. proposer가 30일치 아카이브를 kind 필터 없이 records 잠금 아래에서 읽는다.** 중간 · [확인]
- **근거.** `scheduler.py:1763`의 `iter_records_with_archive(appended_since=...)`에는 `kinds=`가 없다.
  이 결과를 쓰는 쪽은 두 kind만 읽는다. 같은 파일 `:1704`(factory 경로)는 `kinds=`를 넘긴다.
- **실측.** 필터 없이 1,107 ms, 필터를 넘기면 164 ms다. 그동안 리스크 레인의 `crypto_cycle` append는
  최대 1,098 ms 기다렸다. 레인 분리(#733)의 효과를 일부 되돌리는 교차 레인 블로킹이다.
- **설계.** 두 kind를 넘긴다(S). 구조적으로는, 한번 쓴 아카이브는 바뀌지 않으므로 잠금 밖에서 읽고
  잠금은 파일 목록과 활성 파일 크기를 스냅샷하는 동안만 쥔다(M).

**A6. 조용한 성능 저하 경로.** 중간 · [확인]
- **rotation.** 부분 실패가 정상 상태 문자열에 섞여 "fired"로 집계된다(`scheduler.py:1197`). 알림은

**A7. 디스크 사용량을 아무도 감시하지 않는다.** 낮음–중간 · [추정], 크기는 [문서]

### B. 분석 레인(비크립토) — 제품 품질과 신뢰성

**B1. 페일오버가 429/503에서만 일어난다.** 높음 · [확인] · **잠긴 결정이므로 §5 D1에서 재검토 요청**
- **근거.** `providers.py:296` `_RETRYABLE_HTTP={429,503}`이고 그 밖의 오류는 모두 `PROVIDER_TRANSPORT`로
  즉시 실패한다. 키 누락, 401, 404(폐기된 모델 slug), 500/502/504, DNS·연결 거부, 타임아웃, 응답 형식
  오류 모두 다음 멤버로 넘어가지 않는다.
- **이 저장소 스스로 기록한 비용.** Groq 404가 "이 기본값을 쓰는 모든 경로를 한 번에" 멈췄다
  (`providers.py:226-230`, 2026-08-29). 빈 slug 하나가 "9일간의 조용한 장애"를 만들었다(`:383`).
- 잠긴 결정의 근거("4xx는 다른 벤더라도 답이 같다")는 키·slug·형식 오류에는 맞지 않는다. 이런 오류는
  **해당 멤버에만** 해당하기 때문이다.

**B2. 일부 전송 오류가 타입 없는 예외로 샌다.** 높음 · [확인]
- **근거.** `_post_json_with_retry`(`providers.py:325-345`)는 `HTTPError`, `TimeoutError`, `URLError`만
  잡는다. `RemoteDisconnected`, `ConnectionResetError`, `IncompleteRead`는 그대로 올라간다. 워커·triage·
  validator는 `(ProviderError, TimeoutError)`만 잡는다(`worker.py:671`, `triage.py:164`,
  `validator.py:227`).
- **영향.** 연결 리셋 한 번이면 BLOCK 레코드도 감사 기록도 없이 실행이 죽는다. operator 루프에서는
  텔레그램 offset을 이미 저장한 뒤라 요청이 답 없이 사라질 수 있다 [추정].
- **설계.** `OSError`와 `http.client.HTTPException`을 `PROVIDER_TRANSPORT`로 매핑한다. 노력 S이며,
  결정이 필요 없는 버그 수정이다.

**B3. 근거 검증이 사실상 항상 통과한다.** 높음 · [확인]
- **근거.** ref가 없는 fact에는 `model:analysis`가 기본으로 붙고(`worker.py:537`), 이 ref는 evidence에

## 4. 바꾸지 말 것

점검 중 "고치고 싶어 보이지만 옳은 것"으로 판정한 것들이다.

## 7. 범위 밖 / 확인하지 못한 것

- 라이브 호스트의 실제 파일 크기, 디스크 여유, 현재 원장 행 수. 모두 문서 값으로 대체했으므로 A3·A4·A7의
  도달 시점은 추정이다.
- 거래소 키 권한(출금 OFF, IP 화이트리스트). 문서의 주장만 확인했다.
- Hermes 컨테이너 내부(별도 이미지)와 텔레그램 봇 설정.
- CI 러너의 실제 코어 수. D4의 xdist 효과는 4코어 로컬 실측이다.
- 크립토 전략의 수익성 자체. 이 점검은 판정 체계와 증거 속도를 봤고, 전략의 좋고 나쁨은 판단하지 않는다.
