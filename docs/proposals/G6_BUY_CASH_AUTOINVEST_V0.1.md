## 1. 무엇을 하는가

- Thomas가 터미널에서 시나리오 하나를 승인한다(`holdings_board --autoinvest-approve`). 승인 내용은 국내 종목과 정수 주 수량, 그리고 합계 상한(원)이다.
- 보유 자산 실행(scheduler-maint)이 국내 정규장 안의 첫 실행에서 그 시나리오를 한 번만 주문한다. 주문은 시장가 매수, 정수 주, 당일 유효(DAY)다.
- 텔레그램에는 "자동 매수 N건 접수"처럼 개수만 보낸다. 종목과 금액은 로컬 저널에만 남는다(H3).

## 2. 지키는 선

| 선 | 어떻게 |
|---|---|
| 켜는 사람 | `MVP_TOSS_ORDERS=buy_only`(scheduler-maint)가 없으면 주문 어댑터가 만들어지지 않는다. 주문마다 직전에 env를 다시 읽는다. Claude는 이 값을 설정하지 않는다 |
| 방향 | 어댑터에는 매수 메서드 하나만 있다. `side=BUY`는 코드에 고정돼 있다. 매도·정정·취소 메서드는 없다 |
| 시장 | 국내 종목만 주문한다(`toss:domestic:`). 미국 ETF는 달러 주문만 받고 API에 환전이 없어, USD 잔고·환전 경로를 확인할 때까지 열지 않는다 |
| 시간 | `GET /api/v1/market-calendar/KR`의 오늘 정규장 안에서만 주문한다. 시작 5분 뒤부터 종료 30분 전까지다. 휴장이거나 달력을 읽지 못하면 주문하지 않는다 |
| 금액 | 추정 = 현재가(`/api/v1/prices`) × 수량 × (1 + 국내 수수료율, `/api/v1/commissions`; 못 읽으면 0.1%). 추정이 시나리오 상한, 하루 50만 원(KST 하루의 저널 합계), 토스 원화 매수 가능 금액 중 하나라도 넘으면 그날은 시나리오 전체를 주문하지 않고 보류한다. 다음 거래일에 다시 본다. 가격이 조금 올라 매수 가능 금액을 넘는 경우는 토스의 `insufficient-buying-power` 거부가 마지막 방어선이다. 수량을 스스로 줄이지 않는다(Thomas가 승인한 것을 바꾸지 않는다) |
| 종목 | 승인할 때 자동·수동 후보(`store.effective_candidates`)에 있는 국내 종목만 받는다. 오타 하나가 임의의 종목을 사는 일을 막는다. 주문 직전에 `stock_info`로 ACTIVE·ETF를 다시 확인한다 |
| 중복 | `clientOrderId`는 시나리오와 종목에서 정해진다. 주문 전에 저널에 의도를 적고, 그 id가 저널에 있으면 다시 보내지 않는다 |
| 실패 | 거부(400, 401/403, 409 중 `request-in-progress` 외, 422, 429)는 접수되지 않은 것이다. 남은 주문을 멈추고 시나리오를 `stopped`로 닫는다. 시간 초과, 연결 끊김, 5xx, 409 `request-in-progress`는 접수 여부를 모르는 것(`unknown`)이다. 멈추고 알린다. 체결 여부는 다음 실행의 체결 내역 읽기(H6)가 보여 준다. 자동 재시도는 없다. 멈춘 시나리오는 다시 이어 가지 않고, 남은 몫은 Thomas가 새 시나리오로 승인한다 |
| 저널 | 주문마다 POST 전에 `intent` 줄을 적고, 응답 뒤 결과 줄을 적는다. 결과 줄이 없는 `intent`는 `unknown`이다. 그 시나리오는 더 보내지 않고 알린다. 서버의 멱등성은 10분뿐이라, 중복을 막는 것은 저널이다 |
| 토큰 | 보유 자산 피드의 토큰을 같이 쓴다. 새 토큰을 발급하지 않는다(한 클라이언트에 토큰 하나) |
| 기간 | 승인된 시나리오는 7일 안에 실행되지 않으면 만료된다 |

## 2a. 왜 이 모양인가

- **승인은 터미널 명령이다.** 기존 승인 경로(R9 `/approve`, R10 `approval_consumption`)는 "외부·금전 효과가 없는" 기억 승격으로 범위가 묶여 있다(`approval.py`). 그것을 돈이 나가는 주문에 넓히는 것은 별도 거버넌스 결정이다. 그래서 여기서는 쓰지 않는다.
- **실행기는 `store.refresh` 밖에 있다.** `holdings_refresh` 실행 안에서 refresh 다음 단계로 돈다. refresh가 실패해도 주문 단계는 따로 판단하고, 자기 알림은 전달된 뒤에만 기록한다.
- **텔레그램에는 개수와 상태만 보낸다.** 금액과 종목, 보류 사유의 숫자는 로컬 저널에 남고, Thomas 터미널의 `--autoinvest-status`로 본다.

## 2b. 켜는 순서 (Thomas)

1. `.env`에 `MVP_TOSS_ORDERS=buy_only`를 넣고 나서 배포(`compose up -d`)한다. 배포 뒤에 넣으면 scheduler-maint를 한 번 더 올려야 한다.
2. 승인: `docker exec -it thomas-scheduler-maint python -m scripts.holdings_board --autoinvest-approve "069500=1,114260=1,411060=2" --max-krw 200000`. 호스트 root로 직접 돌리지 않는다.
3. 다음 국내 정규장 안의 첫 보유 자산 실행에서 주문된다. 텔레그램 "자동 매수 N건 접수"가 오고, 그다음 실행의 체결 내역 읽기에서 체결이 잡힌다.
4. 끄기: `MVP_TOSS_ORDERS`를 지우고 scheduler-maint를 다시 올린다.

## 2c. 첫 실행 (2026-10-27)

- 시나리오 B의 세 주문 중 KODEX 200 1주와 KODEX 국고채3년 1주는 접수됐고 체결됐다(Thomas가 앱에서 확인).
- ACE KRX금현물 2주는 HTTP 422로 거부됐다. 실행기는 설계대로 멈췄고, 다시 보내지 않았다.
- 거부 사유는 확정되지 않았다. 422에는 주문 가능 금액 부족, 거래 제한, 사전 자격 요건 등 여러 코드가 있는데, 응답에서 토스 코드를 읽지 못했다. 메시지와 requestId도 남기지 않았다.
- 유력한 가설은 시장가 매수의 주문 가능 금액이 상한가 기준으로 묶인다는 것이다. 이 경우 앞의 두 주문이 20만 원 중 약 19.3만 원을 묶는다. 토스 문서에는 이 기준이 없다. 국내 증권사 관행에서 나온 추정이다.
- 그래서 먼저 진단을 보강했다. 거부·unknown 응답에서 코드, 메시지, requestId, 본문 형태를 로컬 저널에 남기고, `--autoinvest-status`에 보인다. 남은 금 2주를 새 시나리오로 다시 실행하면 사유가 남는다. 주문 방식(시장가)은 원인이 확정될 때까지 바꾸지 않는다.

## 3. RB4'' — 정수 주 매수는 5만 원 미만도 낸다

RB4'(5만 원 미만은 이월)는 금액 주문과 소수점 주문의 수수료 대비 크기를 위한 규칙이었다. 정수 주 매수(국내)는 1주 이상이면 금액과 상관없이 낸다. 리밸런싱 계산기(`rebalance.plan`)도 같은 규칙을 따른다. 매도, 금액 주문, 수동 줄(코인)은 계속 5만 원 규칙을 지킨다.

- 시나리오를 스스로 만들어 주문하지 않는다(위 결정 2).
- 미국 ETF를 사지 않는다.
- P3를 열지 않는다.
