# 제안: 네이버 '소상공인 AI' 블로그 콘텐츠 레인 V0.1

상태: 제안 (Thomas 승인 전). 상신 원안의 Phase 1을 **재배열**한다.

---

## 0. 원안이 전제한 것 중 하나가 성립하지 않는다

> "가장 먼저 … '네이버 블로그 포스팅 API 연동'을 요청하는 것이 최우선이다."

**네이버 블로그 글쓰기 API는 2020년 5월 6일자로 종료됐다.** 종료 사유가 이 설계에
직접 영향을 준다 — "API를 통한 광고성 글 대량 제작·게재" 차단이 목적이었다. 즉
자동 발행은 미구현 기능이 아니라 **플랫폼이 명시적으로 닫은 경로**다.

따라서 `naver.post_blog`는 만들 수 없고, 우회(브라우저 자동화)는 기술 과제가 아니라
약관·제재 리스크 과제가 된다. 아래 §4에서 세 경로를 비교한다.

반대로 **리서치 쪽은 API가 오히려 풍부**하다. 원안의 우선순위를 뒤집을 근거가 하나 더
있다: 네이버 검색 노출은 C-Rank/D.I.A. 계열 품질 평가를 거치므로, 자동 대량 발행은
블로그 지수에 역효과다. 주 1–2회 고품질이 자동 대량보다 낫고, 그렇다면 병목은
"어떻게 올리나"가 아니라 **"무엇을 쓸 것인가"**다. 리서치가 진짜 레버리지다.

## 1. 재사용 경계 — 신설할 것이 거의 없다

`CLAUDE.md` 가드레일 "Reuse first"에 따라 기존 소유자가 표현할 수 없는 것만 신설한다.
확인 결과, 상신이 요구한 "전문 에이전트 신설"은 **대부분 이미 존재한다**.

| 원안이 요구한 것 | 이미 있는 소유자 | 판정 |
|---|---|---|
| 콘텐츠 전문 에이전트 | `content.general` v0.4.0 (active, routable) | **신설 불필요** |
| 리서치 에이전트 | `research.general` v0.5.0 (active, routable) | **신설 불필요** |
| thomas-dispatch 호출 경로 | `dispatch_bridge` — `research`/`content` kind 이미 허용, P3 상한 | **신설 불필요** |
| 네트워크 리서치 툴 | `tools.py`의 `search.readonly` + `network_access` 게이트 패턴 | **어댑터만 추가** |
| 초안 파일 저장 | `workspace.py` create-only + `filesystem_write` 게이트 | **신설 불필요** |
| 주간 자동 실행 | `scheduler.py` interval 스케줄, kill switch 연동 | **kind 1개 추가** |

실제로 신설이 필요한 것은 **3개뿐**이다.

1. 네이버 리서치 어댑터 (`tools.py`의 provider 패턴 확장)
2. 스키마 1개: `blog_content_package.v0.1` (초안 산출물의 closed schema)
3. 스케줄 kind 1개: `content_ideation`

## 2. 데이터 소스 — 무엇이 실제로 가능한가

| 목적 | 소스 | 인증 | 얻는 것 |
|---|---|---|---|
| 키워드 실검색량 | 네이버 **검색광고 API** `/keywordstool` (RelKwdStat) | 검색광고 계정 + API 라이선스 (무료) | 월간검색수 PC/모바일, 연관키워드, 경쟁정도 |
| 계절성·급상승 | **데이터랩** 검색어트렌드 API | 개발자센터 앱 | 상대 추이(절대값 아님) |
| 경쟁 강도·포맷 | **검색 API** (blog) | 개발자센터 앱 | 상위 노출 글의 길이/구성/발행일 |
| 발행 후 순위 추적 | 검색 API로 자기 글 노출 위치 조회 | 위와 동일 | 키워드별 순위 시계열 |

**분석 자동화의 한계 (원안 Phase 4에 해당):** 블로그 통계/크리에이터 어드바이저는
공개 API가 없다. 유입·체류 지표는 자동 수집 불가다. 그래서 이 설계는 "발행 후 성과
분석"을 **사전 지표(검색량·경쟁도) + 사후 노출순위 추적**으로 대체한다. 이건 축소가
아니라 실제로 자동화 가능한 유일한 피드백 루프다.

## 4. 발행 경로 — 3안 비교

발행은 `GOVERNANCE_POLICY.yaml`에서 **`external_public_action`**에 해당한다. 이는
`validation.independent_validation_required_for`에 명시되어 있고, 권한 등급으로는
**P5 EXTERNAL_ACTION**이다. 그런데 현재 정의된 `p5_policy_gate`는
`applies_to_scopes: [FINANCIAL_APPROVED_TRADING_USE]` 하나뿐이다 — 즉 **콘텐츠 발행을
승인할 수 있는 P5 게이트는 오늘 존재하지 않는다.**

| | A안: 반자동 (권장) | B안: 메일 발행 | C안: 브라우저 자동화 |
|---|---|---|---|
| 방식 | 초안 패키지 생성까지 자동, 운영자가 검토 후 스마트에디터에 붙여넣고 발행 | 블로그 '메일로 글쓰기' 주소로 전송 | Playwright/Chrome으로 로그인·작성 |
| 약관 | 문제 없음 | 공식 기능 (단 §6 확인 필요) | **위반** — 자동화 프로그램 이용 금지, 계정 제재 |
| 거버넌스 변경 | **0** | 새 P5 scope + `p5_policy_gate` 항목 + 독립검증 경로 | 동일 + 자격증명 취급 (가드레일 위반 소지) |
| 착수 시점 | 즉시 | Thomas 승인 + 거버넌스 개정 후 | 권장하지 않음 |
| 되돌리기 | 발행 전이므로 자명 | 비공개 발행 옵션으로 완화 가능 | 어려움 |

**A안 확정 (Thomas 결정, 2026-08-09).** 이유는 셋 — (1) 거버넌스 변경 없이 오늘 시작할
수 있다, (2) 발행 자동화가 절약하는 시간은 회차당 5분 남짓인데 리스크는 계정 전체다,
(3) 초기에는 사람이 매 건을 읽는 것이 품질 데이터를 쌓는 가장 빠른 길이다.

B안은 발행 리듬이 안정된 뒤 별도 상신으로 올린다. **A안에서 B안으로 가는 비용은 낮다** —
파이프라인은 그대로고 마지막 한 칸만 바뀐다.

## 4b. A안 산출물 — 운영자가 실제로 올릴 수 있는 형태

### 마크다운을 주면 안 된다

스마트에디터 ONE은 HTML 편집 모드가 없고 마크다운을 해석하지 않는다. `##`, `**`를
붙여넣으면 기호가 본문에 그대로 남는다. 따라서 산출물은 **읽는 파일과 붙여넣는 파일을
분리**한다.

```
workspace/blog/<발행예정일>-<슬러그>/
  POST.md     # 사람이 읽는 것 — 근거, 제목 후보, 본문, 태그, 이미지 지시가 한 파일에
  PASTE.txt   # 에디터에 그대로 붙여넣는 것 — 서식 기호 0, 문단 단위 개행만
```

두 파일 모두 `blog_content_package.v0.1` 레코드의 **렌더링**이다. 레코드가 authority이고
파일은 산출물이다 — 스키마는 closed(`additionalProperties: false`)로 두고 생성 시 검증한다.

`POST.md`가 담는 것:

| 절 | 내용 |
|---|---|
| 선정 근거 | 타깃 키워드, 월간검색수(PC/모바일), 경쟁정도, 추이. **숫자와 출처 없이는 초안을 만들지 않는다** |
| 제목 후보 | 3개. 각각 타깃 키워드를 앞쪽에 포함 |
| 본문 | `PASTE.txt`와 동일한 텍스트 + 소제목/인용구/구분선 표시 |
| 편집 지시 | 어느 문단을 소제목으로, 어디에 구분선을, 이미지를 몇 번째 문단 뒤에 |
| 태그 | 최대 30개, 검색량 근거가 있는 것부터 정렬 |
| 발행 전 확인 | 사실 검증이 필요한 문장 목록 (가격·기능·무료범위처럼 바뀌는 정보) |

### 이미지: 생성이 아니라 캡처 지시

원안 Phase 2의 '이미지 생성'은 이 주제에 맞지 않는다. 소상공인 AI 활용 글에서 독자가
필요한 그림은 **실제 도구 화면**이지 생성형 일러스트가 아니다. 생성 이미지는 신뢰도를
떨어뜨리고, 네이버에서 같은 스타일의 AI 이미지가 반복되면 오히려 표식이 된다.

그래서 산출물은 이미지 파일이 아니라 **캡처 지시서**다 — 어떤 도구의 어느 화면을, 무엇이
보이도록, 몇 번째 문단 뒤에 넣을지. 운영자가 5분 안에 찍을 수 있는 단위로 쪼갠다.
(썸네일 1장만 생성형으로 만드는 것은 예외로 둘 수 있다.)

### 주간 운영 루프

```
월 09:00  scheduler(content_ideation) 발화
            └─ research.general: 키워드 3~5개 + 근거 → Hermes 경유 운영자에게 제안
운영자      답장으로 1개 선택  (또는 전부 반려 → 다음 주)
            └─ dispatch(kind=content) → content.general → 패키지 생성
운영자      POST.md 검토 → 캡처 → PASTE.txt 붙여넣기 → 발행
운영자      ★ 발행 URL을 시스템에 돌려준다
            └─ 4주간 타깃 키워드 순위 추적 → 다음 회차 키워드 선정에 반영
```

**★ 표시한 단계가 이 설계의 유일한 취약점이다.** A안에서는 사람이 발행하므로 시스템은
발행 사실도, 최종 본문도 모른다. URL 회수가 빠지면 §2의 순위 추적과 Phase 4 피드백 루프가
통째로 끊긴다 — 조용히, 오류 없이. 그래서 URL 회수를 "하면 좋은 것"이 아니라 **루프의
필수 단계**로 못박고, 발행 예정일 +2일까지 URL이 없으면 운영자에게 리마인드가 가도록
한다. 이것이 A안이 B안 대비 실제로 치르는 유일한 비용이다.

### 품질 상한을 먼저 정한다

주 1편으로 시작한다. 자동 생성이 가능하다고 해서 늘리지 않는다 — §0에서 말한 대로
네이버 품질 평가상 대량 발행은 역효과고, 발행 API가 닫힌 이유 자체가 그것이었다.
증편은 순위 추적 데이터가 4주 이상 쌓인 뒤 판단한다.

        티스토리 6편을 발행해 온 주간 작업이고, 성과 기준도 실재한다(`blog_draft_score`
        표준 + #802의 `published_url` writer로 랭크 추적의 전제 확보). 단 "기존 Agent가
        처리 못 함"은 성립하지 **않는다** — 그래서 아래처럼 새 조직이 아니라 용례만 는다.
      - **§13 (에이전트 분리):** 신규 에이전트 없음. 이미 활성인 `content.general`·
        `research.general` 역할의 재사용이라 분리 질문 자체가 발생하지 않는다.
      - **§14 (부서 신설):** 주간 케이던스가 상설 전문 기능을 만드는 것은 맞다 — 그러나
        부서 기준(복수 에이전트, 독립 운영 책임)에 한참 미달하는 **스케줄 행 한 줄**이다.
        레인은 부서가 아니라 통째로 제거 가능한 단위로 유지한다(`predmarket/` 선례).
      - **§15 (사업조직):** 해당 없음. 블로그는 수익 증거를 주장하지 않는 콘텐츠
        마케팅이며, 사업조직 경로(가설→검증→수익 증거→…)에 올리지 않는다.
      - **§16 (가드레일):** 미래 대비용 에이전트 신설 없음, 태스크당 다중 에이전트 없음,
        검증 안 된 사업의 조직화 없음. 이 확장으로 새로 생기는 것은 스케줄 행 1개이고,
        되돌리는 것도 그 행 하나다(`scheduler_cli disable`/`remove`).
      - **자동 키워드 룰(§J Decision 3):** 같은 날 기본값으로 채택 — 매주 가장 검색량 많고
        이길 수 있는 미사용 키워드를 룰이 고르고, `target=<키워드>`가 주간 예외 경로다.
      - **재검토 조건:** 연속 4주 동안 패키지가 발행으로 이어지지 않으면(같은 `package_id`의
        `published` 행 0 — #802의 writer가 그 증거를 만든다) 이 행의 존치를 재검토한다.
        상설 기능의 유지 근거는 사용이다.
