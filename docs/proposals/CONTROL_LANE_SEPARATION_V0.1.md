## 1. 문제 — 측정된 사실

**`/kill`은 지금 실행 중인 작업을 멈추지 못한다. 다음 작업을 막을 뿐이다.**

`operator_cli`의 루프는 단일 스레드다:

```
while True:
    run_operator_once(...)      # ① poll → ② 메시지 처리 → ③ drain (최대 1건 실행)
```

`run_operator_once` 안에서 폴링(①)은 실행(③)보다 **먼저** 일어난다. 그래서 ③이 도는
동안에는 폴링이 없고, 그 사이 Thomas가 보낸 `/kill`은 ③이 끝난 **다음 pass**에서야 읽힌다.

정확히 말하면 — 그리고 이 구분이 결정의 핵심이다:

| 상황 | 지금 동작 |
|---|---|
| 대기 중인 작업이 있을 때 `/kill` | ✅ 다음 claim 전에 kill을 다시 읽으므로 **실행되지 않음** |
| 실행 중인 작업이 있을 때 `/kill` | ❌ 그 작업이 **끝날 때까지 읽히지도 않음** |
| 실행 중 작업 종료 후 | ✅ 이후 작업 전부 정지 |

`drain_queue`의 주석은 "kill-switch는 **매 claim 전에** 다시 읽는다"고 정확히 말하고 있고
그건 사실이다. 하지만 claim과 claim 사이에 폴링이 없으므로, **그 kill 메시지가 아직 런타임에
도착하지 않았다**는 것이 실제 상태다.

**최악 지연:** 한 작업의 전체 소요 시간. 독립 검증이 붙은 실행은 모델 호출 2회 + M3 revision
1회까지 가능하므로 수 분이다.

### 1.1 이것이 왜 그냥 버그가 아닌가

`kill_switch.agent_can_disable_or_bypass: false`, `runtime_enforcement_active: true`,
`kill_blocks: [new_execution, pending_execution, ...]` — 정책은 "실행을 막는다"고 말하고,
런타임은 그대로 한다. **`pending_execution`은 막힌다.** 지금 도는 것을 되돌리는 것은
`kill_blocks`가 약속한 적이 없다.

그래서 이건 정책 위반이 아니라 **이름과 기대의 불일치**다. `/kill`이라는 이름은 즉시성을
암시하고, 비상 상황에서 사람이 기대하는 것도 즉시성이다. 고칠지 말지가 결정 사항이다.

### 1.2 상쇄 요인 — 그리고 v0.1이 여기서 틀렸다

> ⚠️ **정정 (2026-07-29).** v0.1은 이 절에 이렇게 썼다: *"금융 실행 경로는 이 문제와
> 무관하다. 자율 진입점은 주문 경로를 import할 수 없고, 유일한 문은 canary 스크립트다."*
> **두 절 다 틀렸고, 쓸 당시에 이미 틀렸다.** cycle routing(#302, 2026-07-28 07:53Z)이
> v0.1이 인용한 바로 그 베이스(`a18615e`)에 이미 들어 있었다. tripwire는 "아무도 못
> 한다"에서 "`cycle.py`만, `live_route.py`를 통해서만"으로 바뀌어 있었고, 나는 그것을
> 코드에서 다시 읽지 않고 이전 세션의 기억에서 옮겨 적었다 — v0.1이 스스로 "모든 사실
> 주장은 코드에서 확인했다"고 말하면서.
>
> 이 저장소가 반복해서 기록해온 실패 유형이다(#203 "설계 기록이 거짓이 된 안전 주장을
> 하고 있었다", readiness board의 prose drift). 아래가 코드에서 다시 읽은 사실이다.

**사실 (2026-07-29, `36fd1f7` 기준):**

- **Scheduler는 여전히 별도 컨테이너**다. crypto 사이클은 operator 루프를 붙잡지 않는다.
  `run_due`는 **매 fire 앞에서** `execution_allowed`를 다시 읽는다.
- **라이브 주문 경로에는 이제 자율 호출자가 있다.** `cycle.py` → `live_route.py`가 유일한
  chokepoint이고, tripwire는 그 하나만 허용한다(`operator.py`/`pipeline.py`/
  `scheduler.py`/`domain_console.py`는 여전히 `frozenset()` — 접근 불가).
- **그리고 그 경로는 진입 직전에 kill을 다시 읽는다** (`live_route.py`의
  `control.load().execution_allowed`). 청산 경로는 의도적으로 면제다 — 정지가 열린
  포지션을 가두면 안 되므로.
- operator 루프가 붙잡히는 동안 **그 루프 자신이** 실행하는 비가역 효과는 여전히
  R8 workspace write(`workspace/` 격리, 가역)뿐이다.

### 1.3 그래서 갭은 좁아진 게 아니라 **모양이 바뀌었다**

라이브 경로가 kill을 확인한다는 것은 좋은 소식이다. 문제는 **그 kill이 도착해야 한다**는
것이고, **kill을 수신할 수 있는 프로세스는 operator 루프 하나뿐**이라는 것이다.

```
Thomas가 /kill 전송
   → operator 루프가 폴링해야 읽는다        ← §1의 갭: drain 중에는 폴링이 없다
   → control state 파일에 쓴다
   → scheduler가 다음 guard에서 읽는다      ← 여기는 정상 동작
   → live_route가 진입을 거부한다
```

**즉 operator 루프의 응답성이 이제 금융 경로의 안전 의존성이다.** analysis 한 건이 도는
동안 `/kill`은 런타임 어디에도 존재하지 않고, 그 창 안에서 scheduler의 사이클은 멈췄어야
할 라이브 진입을 라우팅할 수 있다.

**창의 크기:** analysis 1건 (모델 호출 1~2회 + 선택적 revision). 무한하지 않지만 0도 아니다.

이것이 v0.1의 §5 권고가 서 있던 근거를 바꾼다 — v0.1은 "operator 루프는 위험한 것을 아무것도
실행하지 않으므로 갭이 좁다"고 했고, 그 문장은 지금도 참이지만 **더 이상 요점이 아니다.**
operator 루프는 무엇을 실행하는가가 아니라 **무엇을 수신하는가** 때문에 중요하다.

## 2. 무엇을 포기하지 않아야 하는가

어떤 안을 고르든 아래는 유지되어야 한다. 이것이 옵션들의 비용을 결정한다.

1. **Overlap-safe 보장.** 지금의 "동시에 한 작업"은 단일 프로세스라는 사실에서 공짜로 나온다.
   실행을 분리하면 이 보장을 **명시적으로 다시 만들어야** 한다 (`docker-compose.yml`의
   "Run at most ONE scheduler service per state volume"와 같은 종류의 계약).
2. **작업을 잃지 않는다.** kill은 큐를 비우지 않는다 — 멈추는 것이지 버리는 것이 아니다.
3. **`resume_requires_thomas_authentication: true`.** 재개는 언제나 검증된 Thomas의 행동이다.
4. **감사.** 중단된 실행은 "없었던 일"이 아니라 **중단된 일**로 기록되어야 한다.
   지금 registry는 `QUEUED → RUNNING → 종결` forward-only이고, 중단된 RUNNING 항목을
   표현할 상태가 없다 (`CANCELLED`는 QUEUED에서만 온다).

## 3. 옵션

### 옵션 A — 아무것도 하지 않고, 대신 정직하게 적는다

`/kill`의 응답 문구와 문서에 "실행 중인 작업은 끝난 뒤 정지합니다"를 명시한다.

- **비용:** 거의 0 (문구 + 문서).
- **얻는 것:** 기대와 동작의 불일치가 사라진다. 사람이 놀라지 않는다.
- **잃는 것:** 즉시성은 여전히 없다.
- **적합한 경우:** §1.2의 상쇄 요인들을 충분하다고 볼 때.

### 옵션 B — 협조적 중단 (Cooperative abort) ★ 권고

파이프라인이 **단계 경계에서** 중단 요청을 확인하고 스스로 멈춘다.

**핵심: 필요한 이음매가 이미 있다.** PR #294(Progress delivery)가 `run_task`에
`on_progress` 콜백을 6개 단계 경계에 심었다 — 검색 / 분석 / 자동검증 / 독립검증 / 수정 /
쓰기. 같은 지점에서 control state를 다시 읽고, 중단이면 typed 예외로 빠져나오면 된다.

```
검색 → [확인] → 분석(모델 호출) → [확인] → 자동검증 → [확인] → 독립검증(모델 호출) → …
```

- **최악 지연:** 진행 중인 **모델 호출 1회**(수십 초). 지금은 작업 전체(수 분).
- **비용:** 중간. 새 계약/스키마/게이트 없음. 필요한 것:
  - `run_task`에 중단 확인 콜백 (진행 보고와 같은 자리, 같은 fail 방향)
  - registry에 중단된 RUNNING의 종결 상태 — `CANCELLED` 전이 규칙 확장 또는
    `reason_code`를 단 `FAILED`. **여기서 `task_registry_entry` 변경이 필요할 수 있다**
    (§2-4의 감사 요구)
  - drain이 중단 예외를 잡아 항목을 종결하고 Thomas에게 알림
- **한계 (정직하게):** **진행 중인 모델 호출은 끊지 못한다.** 그리고 폴링이 여전히 실행
  뒤에 있으므로, kill 메시지 자체는 그 작업이 끝나야 도착한다 — **즉 옵션 B는 단독으로는
  아무것도 고치지 못한다.** B는 C 또는 D와 **함께여야** 의미가 있다.

> ⚠️ 이 한계는 초안에서 놓칠 뻔했고, 그것이 이 문서에서 가장 중요한 문장이다:
> **중단을 확인할 코드가 있어도, 중단 신호가 도착하지 못하면 소용이 없다.**

### 옵션 C — 폴러와 실행기를 분리 (두 프로세스)

operator 컨테이너를 둘로 나눈다: 폴링·명령 처리만 하는 프로세스와, 큐를 소비하는 워커.

- **얻는 것:** `/kill`이 **즉시 도착**한다. 워커는 B의 확인 지점에서 멈춘다. 둘을 합치면
  최악 지연이 모델 호출 1회로 내려간다.
- **비용:** 높음.
  - `docker-compose.yml`에 서비스 1개 추가 (배포 형태 변경)
  - **overlap-safe 보장을 명시적으로 재구축**해야 함 — 워커는 정확히 1개라는 계약,
    그리고 `claim_next_queued`의 잠금이 프로세스 간에도 충분한지 재검증
  - 두 프로세스가 같은 상태 볼륨을 쓰므로 `state_guard`/uid 규칙 재확인
  - heartbeat/healthcheck 3개로
- **잃는 것:** "단일 프로세스라서 안전하다"는 설명이 더 이상 참이 아니다. 이 저장소가
  여러 곳에서 기대고 있는 문장이다.

### 옵션 D — Control 전용 경량 루프 (한 프로세스, 두 스레드)

같은 프로세스 안에서 폴링만 하는 스레드를 하나 띄운다. 이 스레드는 control verb
(`/kill` `/pause` `/status`)만 처리하고 control state에 쓴다. 실행은 메인 스레드 그대로.

- **얻는 것:** C와 같은 즉시성. 배포 형태는 그대로.
- **비용:** 중간~높음. 컨테이너는 안 늘지만 **동시성이 프로세스 안으로 들어온다** —
  이 저장소가 지금까지 한 번도 하지 않은 것이다. Telegram getUpdates 커서를 두 곳에서
  건드리면 안 되므로(단일 consumer 규칙) 폴링 소유권을 명확히 나눠야 한다.
- **위험:** 두 스레드가 같은 `telegram_offset.json`과 ledger를 만진다. 지금 파일 잠금은
  프로세스 간 잠금이고 스레드 간 재진입은 검증된 적이 없다.

### 옵션 E — 단계 경계에서 **control verb만** 폴링 (v0.2 추가)

§1.3의 재구성이 열어준 안이다. 문제가 "실행을 중단하는 것"이 아니라 "kill을 **수신**하는
것"이라면, 실행을 중단 가능하게 만들 필요가 없다 — **수신만 하면 된다.**

drain 중 각 단계 경계에서(옵션 B와 같은 `on_progress` 자리) 논블로킹 `getUpdates`를 한 번
돌리고, **control verb(`/kill` `/pause` `/status`)만** 처리한다. 나머지 메시지는 커서를
전진시키지 않고 다음 정상 폴링에 맡긴다.

- **얻는 것:** kill이 **단계 경계마다** 도착한다. 최악 지연 = 진행 중인 모델 호출 1회.
  §1.3의 창이 analysis 1건에서 모델 호출 1회로 줄어든다.
- **비용:** 낮음~중간. 새 프로세스도 스레드도 없다. 단일 consumer 규칙도 유지된다 —
  같은 프로세스, 같은 스레드, 순차 실행이다.
- **위험:** **커서 처리가 이 안의 전부다.** `getUpdates`는 offset을 전진시키면 그 전 업데이트를
  다시 주지 않는다. control verb만 처리하면서 커서를 전진시키면 **같은 배치에 섞여 있던
  일반 메시지가 영구히 사라진다.** 그래서 이 안은 "control만 처리하고 커서는 그대로 둔 뒤,
  다음 정상 폴링이 같은 배치를 다시 받아 처리한다"여야 하고 — 그러면 **control verb가 두 번
  처리될 수 있다.** `/kill`은 멱등이라 무해하지만 `/approve`는 아니다. 그래서 이 창에서
  처리하는 verb 집합을 **멱등한 것으로 좁게 고정**하는 것이 설계의 핵심이다.
- **정직하게:** 이 커서 문제는 작지 않다. 옵션 C는 프로세스를 나눠서 이 문제를 **아예 만들지
  않는다**(폴러가 커서의 유일한 소유자로 남는다). E는 싼 대신 미묘하다.

## 4. 옵션 비교

비교의 축이 §1.3에서 바뀌었다. 이제 묻는 것은 "실행 중 작업을 멈출 수 있는가"가 아니라
**"kill이 얼마나 빨리 런타임 안으로 들어오는가"**다 — 라이브 경로는 그것만 있으면 스스로 멈춘다.

| | A | C + B | D + B | **E** |
|---|---|---|---|---|
| kill 수신 지연 (§1.3의 창) | analysis 1건 | **모델 호출 1회** | **모델 호출 1회** | **모델 호출 1회** |
| 실행 중 analysis 중단 | ✗ | ✓ | ✓ | ✗ (수신만) |
| 배포 변경 | 없음 | 서비스 +1 | 없음 | 없음 |
| overlap-safe 재구축 | 불필요 | **필요** | **필요** | 불필요 |
| 프로세스 내 동시성 | 없음 | 없음 | **도입** | 없음 |
| 고유 위험 | — | 상태 볼륨 공유 | 스레드 재진입 | **getUpdates 커서** |

(B 단독은 표에서 뺐다 — §3에서 적었듯 신호가 도착하지 못하므로 단독으로는 아무것도 고치지
못한다. B는 C/D/E의 부속이다.)

## 5. 권고 (v0.2에서 변경됨)

**v0.1의 권고는 "A만 지금, C는 보류"였다. §1.2의 사실 오류가 그 근거의 절반이었으므로
권고를 다시 낸다: A + E를 지금 하고, C는 여전히 보류한다.**

근거:

1. **문제가 바뀌었다.** 사야 하는 것은 "실행 중단"이 아니라 **"kill 수신"**이다.
   `live_route`가 진입 직전에 kill을 재확인하므로, 신호만 제때 들어가면 금융 경로는 스스로
   멈춘다. 이 재구성이 E를 가능하게 하고 C의 필요성을 낮춘다.
2. **E는 §1.3의 창을 analysis 1건에서 모델 호출 1회로 줄이면서 배포도 동시성 모델도 건드리지
   않는다.** C/D가 요구하는 overlap-safe 재구축이 없다.
3. **A는 여전히 필요하다.** E를 해도 즉시는 아니다. `/kill`의 응답 문구는 무엇이 언제
   멈추는지 말해야 한다 — 비상 상황에서 사람이 "멈췄다"고 잘못 믿는 것이 가장 위험하다.
4. **C를 사야 하는 신호를 다시 쓴다.** v0.1은 "금융 경로가 operator 루프에 연결되는 날"이라
   했다. 그 날은 오지 않았고(tripwire가 `operator.py`를 여전히 `frozenset()`으로 막는다),
   대신 **금융 경로가 operator 루프의 응답성에 의존하게 됐다.** 새 신호는 둘이다:
   E의 커서 처리가 실제로 메시지를 잃거나 중복 처리하는 것이 관측될 때, 또는 §1.3의 창이
   실제 사고로 나타날 때.
5. C를 고른다면 D보다 C다 — 프로세스 분리는 scheduler로 한 번 해봤고 스레드 동시성은 해본
   적이 없다.

**E를 하지 않기로 하면**, §1.3의 창은 알려진 채로 남는다. 그것도 유효한 선택이지만
**모르는 채로 남기는 것과는 다르다** — 그 구분이 이 문서의 존재 이유다.
