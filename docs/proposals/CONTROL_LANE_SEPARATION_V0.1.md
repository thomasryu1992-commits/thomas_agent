# 제안: Control Lane 분리 — `/kill`이 실행 중인 작업을 멈추게 할 것인가 (DRAFT)

> **상태: DRAFT — 결정을 위한 문서. 어떤 것도 활성화하지 않으며 구현 착수도 아니다.**
> 요구되는 Thomas 결정은 §6에 있다.
>
> 사실 확인 기준: `main` = `a18615e` (2026-07-28). 아래 §1의 모든 주장은 문서가 아니라
> 코드에서 확인했다. 권한·효과의 authority는 `governance/GOVERNANCE_POLICY.yaml`,
> 현재 구현 사실은 `docs/ACTIVE_ARCHITECTURE.md`.

## 1. 문제 — 측정된 사실

**`/kill`은 지금 실행 중인 작업을 멈추지 못한다. 다음 작업을 막을 뿐이다.**

`operator_cli`의 루프는 단일 스레드다:

```
while True:
    run_operator_once(...)      # ① poll → ② 메시지 처리 → ③ drain (최대 1건 실행)
```

`run_operator_once` 안에서 폴링(①)은 실행(③)보다 **먼저** 일어난다. 그래서 ③이 도는
동안에는 폴링이 없고, 그 사이 Thomas가 보낸 `/kill`은 ③이 끝난 **다음 pass**에서야 읽힌다.

정확히 말하면 — 그리고 이 구분이 결정의 핵심이다:

| 상황 | 지금 동작 |
|---|---|
| 대기 중인 작업이 있을 때 `/kill` | ✅ 다음 claim 전에 kill을 다시 읽으므로 **실행되지 않음** |
| 실행 중인 작업이 있을 때 `/kill` | ❌ 그 작업이 **끝날 때까지 읽히지도 않음** |
| 실행 중 작업 종료 후 | ✅ 이후 작업 전부 정지 |

`drain_queue`의 주석은 "kill-switch는 **매 claim 전에** 다시 읽는다"고 정확히 말하고 있고
그건 사실이다. 하지만 claim과 claim 사이에 폴링이 없으므로, **그 kill 메시지가 아직 런타임에
도착하지 않았다**는 것이 실제 상태다.

**최악 지연:** 한 작업의 전체 소요 시간. 독립 검증이 붙은 실행은 모델 호출 2회 + M3 revision
1회까지 가능하므로 수 분이다.

### 1.1 이것이 왜 그냥 버그가 아닌가

`kill_switch.agent_can_disable_or_bypass: false`, `runtime_enforcement_active: true`,
`kill_blocks: [new_execution, pending_execution, ...]` — 정책은 "실행을 막는다"고 말하고,
런타임은 그대로 한다. **`pending_execution`은 막힌다.** 지금 도는 것을 되돌리는 것은
`kill_blocks`가 약속한 적이 없다.

그래서 이건 정책 위반이 아니라 **이름과 기대의 불일치**다. `/kill`이라는 이름은 즉시성을
암시하고, 비상 상황에서 사람이 기대하는 것도 즉시성이다. 고칠지 말지가 결정 사항이다.

### 1.2 지금 이걸 상쇄하는 것들

- **Scheduler는 별도 컨테이너**다. crypto/prediction 사이클은 operator 루프를 붙잡지 않고,
  자체적으로 매 fire 전에 kill을 재확인한다.
- **금융 실행 경로는 이 문제와 무관하다.** 자율 진입점은 주문 경로를 import할 수 없고
  (tripwire), 유일한 문은 운영자가 직접 실행하는 canary 스크립트다.
- operator 루프가 붙잡히는 것은 **분석 파이프라인 1건**이다. 되돌릴 수 없는 효과는
  R8 workspace write(`workspace/` 격리, 가역)뿐이다.

즉 **지금 이 갭이 실제로 위험한 시나리오는 좁다.** 그것이 §5 권고의 근거다.

## 2. 무엇을 포기하지 않아야 하는가

어떤 안을 고르든 아래는 유지되어야 한다. 이것이 옵션들의 비용을 결정한다.

1. **Overlap-safe 보장.** 지금의 "동시에 한 작업"은 단일 프로세스라는 사실에서 공짜로 나온다.
   실행을 분리하면 이 보장을 **명시적으로 다시 만들어야** 한다 (`docker-compose.yml`의
   "Run at most ONE scheduler service per state volume"와 같은 종류의 계약).
2. **작업을 잃지 않는다.** kill은 큐를 비우지 않는다 — 멈추는 것이지 버리는 것이 아니다.
3. **`resume_requires_thomas_authentication: true`.** 재개는 언제나 검증된 Thomas의 행동이다.
4. **감사.** 중단된 실행은 "없었던 일"이 아니라 **중단된 일**로 기록되어야 한다.
   지금 registry는 `QUEUED → RUNNING → 종결` forward-only이고, 중단된 RUNNING 항목을
   표현할 상태가 없다 (`CANCELLED`는 QUEUED에서만 온다).

## 3. 옵션

### 옵션 A — 아무것도 하지 않고, 대신 정직하게 적는다

`/kill`의 응답 문구와 문서에 "실행 중인 작업은 끝난 뒤 정지합니다"를 명시한다.

- **비용:** 거의 0 (문구 + 문서).
- **얻는 것:** 기대와 동작의 불일치가 사라진다. 사람이 놀라지 않는다.
- **잃는 것:** 즉시성은 여전히 없다.
- **적합한 경우:** §1.2의 상쇄 요인들을 충분하다고 볼 때.

### 옵션 B — 협조적 중단 (Cooperative abort) ★ 권고

파이프라인이 **단계 경계에서** 중단 요청을 확인하고 스스로 멈춘다.

**핵심: 필요한 이음매가 이미 있다.** PR #294(Progress delivery)가 `run_task`에
`on_progress` 콜백을 6개 단계 경계에 심었다 — 검색 / 분석 / 자동검증 / 독립검증 / 수정 /
쓰기. 같은 지점에서 control state를 다시 읽고, 중단이면 typed 예외로 빠져나오면 된다.

```
검색 → [확인] → 분석(모델 호출) → [확인] → 자동검증 → [확인] → 독립검증(모델 호출) → …
```

- **최악 지연:** 진행 중인 **모델 호출 1회**(수십 초). 지금은 작업 전체(수 분).
- **비용:** 중간. 새 계약/스키마/게이트 없음. 필요한 것:
  - `run_task`에 중단 확인 콜백 (진행 보고와 같은 자리, 같은 fail 방향)
  - registry에 중단된 RUNNING의 종결 상태 — `CANCELLED` 전이 규칙 확장 또는
    `reason_code`를 단 `FAILED`. **여기서 `task_registry_entry` 변경이 필요할 수 있다**
    (§2-4의 감사 요구)
  - drain이 중단 예외를 잡아 항목을 종결하고 Thomas에게 알림
- **한계 (정직하게):** **진행 중인 모델 호출은 끊지 못한다.** 그리고 폴링이 여전히 실행
  뒤에 있으므로, kill 메시지 자체는 그 작업이 끝나야 도착한다 — **즉 옵션 B는 단독으로는
  아무것도 고치지 못한다.** B는 C 또는 D와 **함께여야** 의미가 있다.

> ⚠️ 이 한계는 초안에서 놓칠 뻔했고, 그것이 이 문서에서 가장 중요한 문장이다:
> **중단을 확인할 코드가 있어도, 중단 신호가 도착하지 못하면 소용이 없다.**

### 옵션 C — 폴러와 실행기를 분리 (두 프로세스)

operator 컨테이너를 둘로 나눈다: 폴링·명령 처리만 하는 프로세스와, 큐를 소비하는 워커.

- **얻는 것:** `/kill`이 **즉시 도착**한다. 워커는 B의 확인 지점에서 멈춘다. 둘을 합치면
  최악 지연이 모델 호출 1회로 내려간다.
- **비용:** 높음.
  - `docker-compose.yml`에 서비스 1개 추가 (배포 형태 변경)
  - **overlap-safe 보장을 명시적으로 재구축**해야 함 — 워커는 정확히 1개라는 계약,
    그리고 `claim_next_queued`의 잠금이 프로세스 간에도 충분한지 재검증
  - 두 프로세스가 같은 상태 볼륨을 쓰므로 `state_guard`/uid 규칙 재확인
  - heartbeat/healthcheck 3개로
- **잃는 것:** "단일 프로세스라서 안전하다"는 설명이 더 이상 참이 아니다. 이 저장소가
  여러 곳에서 기대고 있는 문장이다.

### 옵션 D — Control 전용 경량 루프 (한 프로세스, 두 스레드)

같은 프로세스 안에서 폴링만 하는 스레드를 하나 띄운다. 이 스레드는 control verb
(`/kill` `/pause` `/status`)만 처리하고 control state에 쓴다. 실행은 메인 스레드 그대로.

- **얻는 것:** C와 같은 즉시성. 배포 형태는 그대로.
- **비용:** 중간~높음. 컨테이너는 안 늘지만 **동시성이 프로세스 안으로 들어온다** —
  이 저장소가 지금까지 한 번도 하지 않은 것이다. Telegram getUpdates 커서를 두 곳에서
  건드리면 안 되므로(단일 consumer 규칙) 폴링 소유권을 명확히 나눠야 한다.
- **위험:** 두 스레드가 같은 `telegram_offset.json`과 ledger를 만진다. 지금 파일 잠금은
  프로세스 간 잠금이고 스레드 간 재진입은 검증된 적이 없다.

## 4. 옵션 비교

| | A | B 단독 | C + B | D + B |
|---|---|---|---|---|
| 실행 중 작업 중단 | ✗ | ✗ (신호가 안 옴) | ✓ | ✓ |
| 최악 지연 | 작업 전체 | 작업 전체 | 모델 호출 1회 | 모델 호출 1회 |
| 새 계약/스키마 | 없음 | registry 상태 1개 | registry 상태 1개 | registry 상태 1개 |
| 배포 변경 | 없음 | 없음 | 서비스 +1 | 없음 |
| overlap-safe 재구축 | 불필요 | 불필요 | **필요** | **필요** |
| 프로세스 내 동시성 | 없음 | 없음 | 없음 | **도입** |

## 5. 권고

**A를 지금 하고, C+B를 조건부로 보류한다.**

근거:

1. **B 단독은 무의미하고, C/D는 이 저장소가 지금까지 피해온 성질(다중 실행 주체)을
   도입한다.** §1.2 기준으로 지금 실제 위험이 좁으므로, 그 성질을 지금 사는 것은 이르다.
2. **A는 진짜 문제를 하나 고친다** — 기대와 동작의 불일치. 비상 상황에서 사람이 "멈췄다"고
   믿는 것이 가장 위험하다.
3. **C를 사야 하는 신호는 명확하다:** operator 루프가 되돌리기 어려운 효과를 실행하게 되는
   날. 오늘 그 경로는 R8 workspace write(가역, 격리) 하나뿐이다. **금융 경로가 operator
   루프에 연결되는 날이 오면 C는 선택이 아니라 전제조건이다.**
4. C를 고른다면 D보다 C다. 프로세스 분리는 이 저장소가 이미 (scheduler로) 한 번 해봤고,
   스레드 동시성은 해본 적이 없다.

**A만 하기로 하면**, 이 문서는 "왜 즉시성을 사지 않았는가"의 기록으로 남는다.
