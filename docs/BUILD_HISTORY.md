# Build History — what has been delivered, and why each piece is shaped that way

**This file is a record, not an instruction.** It holds the delivery history that used to live in
`CLAUDE.md`'s Status section. It was moved for one concrete reason: that section had grown to
roughly two thirds of a file every session loads in full, and — worse — it was one of **four**
places claiming project status, which is how the readiness board came to describe a shipped module
as missing for a day. Status now has fewer owners:

| Question | Answer lives in |
|---|---|
| What are the rules I must follow? | `CLAUDE.md` |
| What is still to build? | `docs/REMAINING_WORK.md` |
| What was built, and why is it shaped this way? | **this file** |
| Can this machine place a live order right now? | `python -m runtime.mvp_runtime.crypto.live_readiness` (computed, never prose) |

Nothing here was rewritten or summarised on the move — the entries are verbatim, because their
value is in the reasoning, not the headline. Read it when you need to know *why* something is the
way it is before changing it; a surprising amount of what looks like an odd choice is a recorded
decision with a failure behind it.

Append a new entry when a milestone ships, in the same PR.

Its own store file, so §12.4 retention cannot age out a rung that must not expire. Naming is disambiguated on purpose: a **Core Release Candidate** is a versioned Core document in the release lifecycle; a **Core Candidate** is a sentence with provenance. Promotion to Core is deliberately unbuilt — `runtime_effect.core_activation_allowed` is false and the release lifecycle owns that door.

- Also done: **§10.4 perspective separation** (`worker.PERSPECTIVES`/`PERSPECTIVE_INSTRUCTION`/`_perspectives`, `validation`'s `perspective_separation` check, `general.specialist` output contract 0.3.0 → **0.4.0**, both vendor analysis schemas; 2026-07-27). Organization Architecture §10.4 describes a complex strategy task as several perspectives reaching their own judgement before an integrated decision; the runtime had **no perspective concept at all**. Built in the form §10.4 itself permits for early MVP — *"one Agent may separate these perspectives internally"* — because §13's 3-of-6 criteria for making them three Agents are not met and §16 warns against exactly that. **The failure it prevents is specific**: a single blended narrative in which a weak revenue case is smoothed over by an enthusiastic research case, with the reader unable to see it happened. So the separation is not a prompt convention — the role contract **declares** `perspectives` (each `{perspective, verdict, basis}`, verdict POSITIVE|MIXED|NEGATIVE) and validation refuses an output that skips a perspective, or that reports a NEGATIVE perspective while stating no risk at all. Both conditions are **compliance, not analytical skill** — neither reads prose, so neither can be argued with; same nature as the existing calibration check. Scoped by `required_role_output_keys is None`, so a candidate-role trial (which passes its own declared keys) is excluded **by the role contract rather than by a hardcoded role id**. `_perspectives` **never repairs**: an unknown perspective, unknown verdict or empty basis is dropped, because "did not answer" and "answered badly" both mean the separation did not happen and a normalized entry would hide the case the check exists to catch; first entry wins per perspective so a repeat cannot overwrite its own verdict; output order is the declared order so two runs with the same verdicts produce the same record. **The load-bearing plumbing detail:** `perspectives` had to join the shared vendor response schemas, not just the specialist prompt — the OpenAI dialect is strict (`additionalProperties: false`), so a key the schema does not name is *rejected*, and the specialist would have been asked for a field the transport refused, failing its own check on every hosted run. It rides on the same terms as the other keys (required KEY, no `minItems`) so the validator and triage return `[]` rather than inventing content. `verdict` is a plain string rather than an enum: the two vendor dialects differ on enum support and an unsupported keyword fails the whole request — one REVISE beats an outage. Role version bumped with the contract (`semantic_versioning_required`), registry hash updated, and a **new test pins the contract against what the worker emits** — nothing previously compared them, which is how a drift like this starts. The change grants nothing: ceiling, allowlists, external-action and memory-write flags are asserted unchanged.
- Also done: **§8.5 routing to more than one Role** (registry + definition activation of `research.general` / `translation.general`, `planner.REQUEST_KIND_CAPABILITIES` + `capabilities_for_request_kind`, `worker.build_role_prompt`, `pipeline._role_execution` / `_provider_for_role`, `cli --kind`; **explicit Thomas decision 2026-07-27**). Two things had to be true together, and shipping either alone would have been worse than shipping neither. **Activation alone routes nothing**: every task asked for `("research","analysis")`, which only `general.specialist` has, so the newly-routable Roles were reachable by nobody. **Derivation alone breaks runs**: with one routable Role a derived capability set can only refuse work that used to succeed. Done together they compose, and the capability vocabularies turned out disjoint, so there was no `AMBIGUOUS_ROLE` risk. **A request kind names CAPABILITIES, never a Role** — the Registry stays the only thing that decides which Role covers a set, so activating or retiring a Role changes routing without touching the table; a test asserts no kind's capabilities collide with a role id, and another resolves every kind against the **live** registry so an overlapping activation fails in CI rather than at run time. The kind is **explicit** (`--kind`), not inferred from the request text: inferring "this looks like a translation" is a guess, and a wrong guess routes to a Role with a different output contract — the reader would get a confident answer of the wrong shape. An unknown kind is **refused**, never defaulted to analysis. Omitting it is byte-identical to the pre-§8.5 routing. The second half is that the selected Role runs against **its own** contract: `load_role_definition` and `role_output_spec` moved from `trial.py` to `planner.py` (they were never trial concepts, and a second copy is how "one loader for the whole runtime" stops being true), and a non-default Role gets a role-generic prompt built from its purpose, quality criteria and declared keys — distinct from the trial prompt, which additionally claims "no tools, no web access, no memory", true in an isolated trial and false for a routed run. **Found only by running it**: a routed run then failed its own output check, because the default `MockProvider` answers the business-analysis shape. The trial path already had the answer (`MockTrialProvider`, a mock built from the role's spec), so it moved to `worker.py` beside `MockProvider` and the routed path reuses it. The deeper finding is recorded rather than papered over: the **hosted** response schemas are strict (`additionalProperties: false`) and name only the analysis keys, so a hosted model structurally cannot return `translated_text` — a network provider is now refused **by name** (`ROLE_OUTPUT_CONTRACT_UNSUPPORTED_BY_PROVIDER`) instead of producing a REVISE that reads like a model quality problem when it is a transport contract problem. Making the schema role-aware is the remaining piece, and a test pins the premise so the refusal gets revisited rather than left standing once it is. Activation itself is recorded **in the registry**, not only in a commit message, including that no trial report backed it. Side effect worth knowing: `research.general` being active means a trial of it is now the contradiction `select_candidate_role` refuses, so the trial tests moved onto roles that are still candidates.
