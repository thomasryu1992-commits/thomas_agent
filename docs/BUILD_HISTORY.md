# Build History — what has been delivered, and why each piece is shaped that way

**This file is a record, not an instruction.** It holds the delivery history that used to live in
`CLAUDE.md`'s Status section. It was moved for one concrete reason: that section had grown to
roughly two thirds of a file every session loads in full, and — worse — it was one of **four**
places claiming project status, which is how the readiness board came to describe a shipped module
as missing for a day. Status now has fewer owners:

| Question | Answer lives in |
|---|---|
| What are the rules I must follow? | `CLAUDE.md` |
| What is still to build? | `docs/REMAINING_WORK.md` |
| What was built, and why is it shaped this way? | **this file** |
| Can this machine place a live order right now? | `python -m runtime.mvp_runtime.crypto.live_readiness` (computed, never prose) |

Nothing here was rewritten or summarised on the move — the entries are verbatim, because their
value is in the reasoning, not the headline. Read it when you need to know *why* something is the
way it is before changing it; a surprising amount of what looks like an odd choice is a recorded
decision with a failure behind it.

Append a new entry when a milestone ships, in the same PR.

## Delivered

- Also done: **A directional cap on the paper portfolio — the third cap, and the first that reads the book's shape rather than its size** (`crypto/paper.py`, `crypto/cycle.py`, `crypto/dashboard.py`; 2026-07-30). The portfolio-level authority the cross-sectional entry below left explicitly open, shipped as **the part that can be one-directional**. `MAX_CONCURRENT_POSITIONS` (20) and `MAX_POSITIONS_PER_SYMBOL` (4) bound how *many* positions exist and how many share a symbol; **neither bounded how many point the same way**, so twenty simultaneous longs were permitted — the F1 hazard `docs/TRADING_STRATEGY_REVIEW_RECORD.md` names, where one market move becomes twenty correlated verdicts about twenty different strategies. `paper.directional_skew_admits` is a third refusal inside the SAME portfolio lock, counted from the `open_books` the two existing caps already had in hand — no new chokepoint, no extra read, and the lock is what stops two cycles from each counting before either wrote. **What was deliberately NOT built, and why that is the whole shape of this increment:** balancing k long against k short requires *creating* the opposing position, which is the runtime inventing an entry no strategy proposed — a new authority over money and a Thomas decision. What shipped can only ever **decline**, which is the `regime_admits` / `vol_size_multiplier` posture and the reason it needs no gate of its own. So this is exposure **discipline**, not enforced market neutrality; the difference is stated in the research record rather than blurred. **The cap is derived, not chosen:** it IS `MAX_POSITIONS_PER_SYMBOL`, so the rule has an English statement with no number in it — *the portfolio's net directional bet may never exceed one symbol's full allocation.* And it is provably **not a concurrency cap in disguise**, which is what makes the derived value right rather than merely tidy: at 20 slots a book of 12 long + 8 short is net 4, so the full portfolio limit stays reachable and what is forbidden is a full book that is *one-way*. A test pins exactly that, because a cap that silently shrank the portfolio would look identical from outside. **The sign convention is load-bearing and a reader will want to "simplify" it back:** everything is counted *toward the proposal* (`aligned`, `opposing`, lean = `aligned - opposing`), so the rule is one comparison and the corrective-safe property falls out for free — a lean that would exceed the cap is only reachable from a book that already leans that way, so an entry that *reduces* an imbalance is never declined. Written as `abs(new_skew) > cap` it looks equivalent and is not: once unsynchronised exits have pushed the book past the cap on its own, that form refuses the very trades that would rebalance it. **Measured, on a 1,200-bar five-symbol twenty-context simulation driven by the shipped function:** the absolute form blocked corrective entries for no gain (identical opened count, identical worst-case lean), and the shipped rule cut the time the book spent leaning more than one symbol's worth from **16.3% to 2.3%** and the worst observed lean from **8 to 6**, for **2.9% fewer positions opened** (452 → 439) and a mean book size of 8.6 → 8.3. Worth stating that the no-cap worst case was 8 against a mean book size of 8.6 — **at times the entire book was one direction**, on five *independent* random walks; the mock's own `ref_correlation` runs ±0.05 between symbols where real majors run +0.7..+0.9, so every number here is a **floor**, not an estimate. **The limit is read from the module global at call time and is deliberately not a parameter**, matching its two siblings — a `cap=MAX_DIRECTIONAL_SKEW` default argument binds the number at import, and that is not hypothetical: it is what the first version did, and the end-to-end test caught it opening a position the cap was set to refuse. **An entry-time gate cannot bound the book thereafter, and the alternative is worse:** exits are unsynchronised, so a balanced 12/8 book becomes 12/0 when the shorts time out — which is why the honest claim is "the skew this runtime deliberately takes on", and why the book still sits over the cap 2.3% of the time. Bounding it after the fact would mean closing positions the strategies did not close: a new authority over exits that would falsify the outcome record paper exists to produce. **Live is untouched, and not by omission** — at `live_position.MAX_LIVE_CONCURRENT_POSITIONS = 2` the live book's largest possible lean is 2, so a cap there is either inert or halves an already-tiny capacity, and live one-way risk is already governed by the operator-registered `max_open_notional_usdt`: that authority exists and is Thomas's number, not one this runtime should second-guess. A test is the tripwire rather than the comment — raise live concurrency past the paper cap and it fails, which is exactly when someone must decide whether live needs its own answer. **Observability was a pre-existing gap this widened and therefore fixed:** `open_refused` reached the ledger only inside `paper_records`' event stream and never the status line, so both count caps have been invisible to anyone reading a fire — tolerable while they fired at twenty positions, not once a third cap can decline a *half-full* book. It is now on the cycle record and the status line with the book's shape attached (`refused=...(LONG 4v0 lean=5>4)`), because "the book leans 5 against a limit of 4" is the actionable part and a bare reason code is not. And the lean is on the **dashboard**, derived at read time and never stored — the `pool.candidate_quality` rule, sharpened here because `MAX_DIRECTIONAL_SKEW` derives from a constant that has already moved once. It belongs on the board and not only on the per-fire line because the gate declines on *standing* state: an operator who missed the one fire that printed a refusal still needs to see the book is one-way. Positions whose direction is neither LONG nor SHORT are **counted, not dropped**, on the board and in the gate — the gate treats them as aligned with whatever is proposed (so a corrupted record makes the cap bind *sooner*, the `list_open_positions` failure direction), and a board that omitted them would show a book more balanced than the one the gate is judging. One more thing the tests caught rather than the author: `render_status_text` is handed status dicts built by older builds and by hand, so gating the new line on the FIELD rather than on `open_positions` is what keeps the board from crashing on exactly the history an operator opens it to read.
- Also done: **Cross-sectional context — the first feature whose value depends on symbols the cycle is not trading** (`crypto/market_data.py`, `crypto/features.py`, `crypto/cycle.py`, `crypto/factory.py`, `scheduler.py`; 2026-07-30). Item 8 / T3-3 of `docs/TRADING_ALPHA_RESEARCH_RECORD.md`, the last on that list and the one it called "biggest expected value, biggest change". **It shipped as half of what the note described, and the half is named rather than quietly redefined.** The note listed three blockers — `route_entries` is single-symbol premised, `symbol_scope` is effectively single-symbol, the position book is (symbol, timeframe) keyed — and **none of them is touched here.** Instead the cohort rank became a *feature*: `xs_rank_pct`, `xs_excess_roc_4`, `xs_dispersion_ratio` (mintable) plus `xs_dispersion` and `xs_members` (evidence), so "long the top k, short the bottom k" is expressible in the existing declarative spec language, scored by the existing backtest, and judged by the existing robustness gate. **No new authority over entries exists, which is the reason to prefer this shape** — the alternative was a portfolio layer that overrides what specs propose, and that is a governance change, not a feature. **What is therefore NOT delivered:** the note claimed market beta "structurally cancels", and that cancellation only happens while longs and shorts are held *simultaneously*. Here it happens probabilistically, when both families fire — it is not enforced. Saying so is the point; a reader who assumed the structural version shipped would be wrong about the runtime's exposure. **`rel_strength_roc_4` could not have substituted, and the reason is worth keeping:** it measures against ONE proxy, so every altcoin can beat BTC in the same hour and the column cannot say which of them to buy — and it says nothing at all about which to sell. A rank answers both. **The cohort is a declared constant (`CROSS_SECTION_UNIVERSE`, six large-cap perps), not "whatever the pool routes today"**, and that is the load-bearing decision: a rank is a statement *about a cohort*, so a cohort that followed the pool would make `xs_rank_pct >= 0.8` mean "strongest fifth of six" at mint time and "strongest fifth of three" after two demotions — same threshold, different claim, nothing in the record showing the substitution. Worse, the cohort would then depend on the pool, which depends on the backtests, which were scored against the cohort. Editing the tuple invalidates every `xs_*` backtest mined under the old cohort, exactly as editing `ROC_FAST` does; `xs_members` rides on the row so a record shows what its rank was actually computed over. **Six members, chosen by arithmetic:** `xs_rank_pct` has only `members - 1` distinct values, so three symbols offer {0, 0.5, 1.0} and a mined threshold is a choice among three buckets — and twenty would be twenty candle series per timeframe per fan-out. `MIN_CROSS_SECTION_MEMBERS = 4` is the floor below which no rank is reported at all, because a two-member rank is a coin flip wearing a six-member column name. **Degradation is per peer, and that is a deliberate divergence from `attach_reference`**: there one series either arrived or the leg was indeterminate; here five of six is a usable cohort, and refusing to rank because the sixth timed out throws away a measurement the runtime has. So the cohort thins, `xs_members` records how many answered, and `CROSS_SECTION_DEGRADED` fires when any peer failed — visible in the record rather than only in a column nobody reads. **Peer momentum comes from `indicators.roc`, not from the full pipeline, and that is what makes six members affordable**: `_reference_columns` recurses into `build_feature_rows` because it needs `ref_market_regime` (a classifier over many columns), but the only peer quantity wanted here is the same `roc` call `build_feature_rows` itself makes — so it is the same authority, not a second one, and it is six `roc` calls instead of six 25-indicator pipelines over a window that is 12,000 bars deep in the factory. Alignment is the **exact open-time join** via `_same_grid_column` — the fourth consumer of that rule — because peers are requested AT this frame's interval; a bar the venue skipped drops that peer rather than carrying its previous value forward, which would rank this symbol against a stale reading. **`ReferenceCandleCache` became `PeerCandleCache`**, generalized by one `symbol` argument rather than duplicated, because the concept is "one candle read per (symbol, timeframe, depth) per fan-out" and a cached read has no opinion about which leg wanted it. That generalization is not cosmetic: this leg is the largest redundancy surface in the runtime — measured on the shipped 5x4 grid, **116 peer reads without the cache and 24 with it**, against a pre-change baseline of 4. Both legs therefore share one default depth (240): a different default would make the proxy's series a cache MISS between the two legs, two reads for one answer. **The 24 still overlap the fan-out's own 20 context reads and that is left alone on purpose** — routing a context's collection through a cache would put its provenance record behind a cache, and the ledger keeps that record to prove what data a cycle saw. Net cost is +20 klines reads per 15-minute fire, well inside the venue's weight budget. **The long and short legs share one `xs_rank_edge` parameter capped below 0.5, and that is a safety property rather than tidiness:** long requires `rank >= 1 - edge`, short requires `rank <= edge`, so the two are DISJOINT across the whole param space. Independent floor/ceiling params could be mined into an overlap (long >= 0.4 while short <= 0.6), and a long and a short matching on one feature row is `paper.BLOCK_DIRECTION_CONFLICT` — the pair failing closed on exactly the bars it was minted for. A test asserts the property of the SPACE, not of one mined value. **`xs_dispersion_ratio` is self-calibrating for the `atr_pct_reference` reason** — a dispersion LEVEL would be a number nobody authorized and would mean one thing at 1h and another at 4h, so the mintable column is a ratio to its own rolling median (measured median 1.000, range 0.317-2.062 on a 400-bar mock frame), and `ParamSpec(0.8, 1.6)` is well-scaled by construction rather than by a guess. `CROSS_SECTION_FAMILIES` gates on cohort size and **does not bind today**, which is why it needs a test: shrink the universe below the floor and every `xs_*` column is permanently None, so the families would still mint, still backtest, take zero trades, and be retired as FRAGILE — the family blamed for a cohort too small to rank. Unlike htf_* and session_*, nothing about a coarser bar makes a rank undefined, so these survive at 1d, where the library is otherwise thinnest (now 32 families at 1h, 26 at 1d). **Measured, not asserted:** on mock candles the rank is near-uniform across its six buckets and determinate on 296/300 bars, both legs fire on ~16% of 2,000 bars, and a 6,000-bar backtest closes 207 trades across all six regimes. **No claim of edge, same as every entry above it:** that backtest lands PROVISIONAL with negative expectancy, which is the correct verdict for a hash-derived random walk and says only that the families are reachable and scoreable.
- Also done: **Volatility-scaled live sizing — the risk taken was rising with volatility** (`crypto/paper.py`, `crypto/live_sizing.py`, `crypto/features.py`, `crypto/indicators.py`; 2026-07-30). Item 7 of `docs/TRADING_ALPHA_RESEARCH_RECORD.md`, and the note's own prescription was wrong in a way its own caveat predicted. It said to make `risk_fraction` a function of volatility, and warned that the budget cap might bind first. Measured: the cap binds for essentially every realistic account — at a 60 USDT per-order cap the risk leg only wins below roughly **30 USDT of equity** — so scaling `risk_fraction` is **provably inert**, which is precisely the "looks like it does something" outcome this repo keeps catching. **The measurement then found something worse than inertness.** While the cap binds the notional is FIXED, so the risk actually taken is `cap × stop_distance / price` and therefore **rises with volatility**: across plausible stop distances at one cap, 0.18 → 1.20 USDT, a factor of **6.7**, biggest bets on the most chaotic tape. That is the opposite of volatility targeting, and it was the live behaviour. So the multiplier applies to the **final quantity**, after `min(risk, budget)` — which is what makes it work through whichever leg bound. Verified: risk taken goes from 0.600/1.200 USDT at 2x/4x normal volatility to a **constant 0.300**, equal to what the reference volatility itself takes. **Capped at 1.0, and the name says so.** `vol_size_multiplier` can only shrink an order. Letting it exceed 1.0 would size above the operator's registered per-order cap in quiet markets — widening an authorization from inside the runtime, which is a Thomas decision and not a multiplier's business. So this is a volatility-scaled **ceiling**, not a two-sided target: in unusually quiet conditions it leaves size where the cap already put it rather than reaching for a risk target. Same one-directional posture as the regime gate, for the same reason. **No target-volatility constant exists**, deliberately: the ratio is `atr_pct_reference / atr_pct_of_price`, both measured from the same series, so there is no number anybody failed to authorize (the #356 lesson) and none that would mean one thing on BTC and another on DOGE. The reference is a **rolling median**, not a mean, and the direction of that error is the argument: its consumer *divides* by it, so a reference dragged upward by the very spikes it should react to yields a LARGER multiplier — less de-risking, the unsafe direction. `indicators.rolling_median` is a non-port like `rolling_correlation` and says so. **A limitation stated rather than hidden:** the floor (0.25) means past 4x the reference volatility the reduction stops tracking — risk is 4x smaller than it would have been, not constant, and a test pins exactly that rather than implying constancy everywhere. Below the floor the venue's own minimum quantity and notional refuse the entry, which is where a refusal on a chaotic tape should come from. **What was investigated and deliberately NOT changed:** live sizing uses `live_sizing.RISK_PER_TRADE_FRACTION` rather than the operator-registered `risk_limits.risk_per_trade`, which looked at first like #356's defect in the one place that moves money. It is not — the constant's own docstring already makes the argument (the fraction can only ever produce a size *below* the registered USDT caps, so it cannot widen an authorization, and making it tunable is a schema bump), and `risk_limits.risk_per_trade` has a different job: converting `max_drawdown_pct` into an R limit for the C4 breaker. Wiring one into the other would make a single number serve two authorities. Paper is untouched by construction, not by omission: its accounting is R-based and R is normalized by risk, so no quantity exists there for a multiplier to scale — this is a live-path change, and the multiplier rides on the plan (like `max_holding_bars`) so the execution step reads it rather than re-deriving a number the two could disagree about. `vol_size_multiplier` is recorded on every sizing record including refusals and including 1.0, because "the scaler did nothing" and "there was no scaler" are different statements and the second is what every record before this said.
- Also done: **Regime-conditional routing — decline a regime a strategy has demonstrated it loses in** (`crypto/paper.py`, `crypto/factory.py`, `crypto/cycle.py`, `scripts/promote_strategy_candidates.py`; 2026-07-30). Item 6 of `docs/TRADING_ALPHA_RESEARCH_RECORD.md`, and it was not the change that document predicted. The note said the evidence was already there — *"`backtest_evidence.regime_breakdown` already computes per-regime R totals, so the routing just has to read it"* — and **both halves of that were wrong**: `backtest_spec` computed `regime_r` per regime and then collapsed it to `sorted(regime_r)` plus a profitable-count, throwing away the only thing that says *where* the edge was; and the pool entry carried `champion_score`, `candidate_id`, `strategy_rule_hash`, `generation_id` and the spec, but **no evidence at all**, so the router had nothing to consult even if it had been kept. So the increment is three things: preserve `per_regime` on the evidence, copy it onto the pool entry at promotion, and gate routing on it. **Why the pool entry rather than a candidate-store lookup:** the router reads the pool, and making it resolve `candidate_id` against the candidate store would put a 359-row store whose reader deliberately **raises** on damage — because it backs a promotion an operator signs — on the path of every 15-minute cycle, so one corrupt line would stop routing. `champion_score` is already on the entry for exactly this reason; this follows it. **The raw numbers, never a derived exclusion list**, and that is a scar this repo already carries: `pool.candidate_quality` had to stop reading stored robustness verdicts because they were written once at mint time, the rule that produced them changed, and twelve candidates kept a label the new rule could not produce — inverting the shortlist on precisely the property the new rule existed to enforce. A baked `excluded: [...]` would repeat that the first time the threshold moved, so `paper.regime_admits` owns the rule and applies it at read time. **The gate's whole design is the direction it fails in.** It can only ever make the pool trade *less* — it never admits an entry the existing checks refuse, which is why it needs no gate of its own — and the cost of a wrong exclusion is **silent**, since no record shows the trades that did not happen. So every uncertain case admits: no `regime_evidence` (every strategy promoted before this), a regime the replay never traded, a malformed cell, an unreadable regime label. Only "traded enough, and lost" declines. `MIN_REGIME_TRADES_TO_EXCLUDE = 10` reuses `robustness.HEALTHY_TRADES_PER_PARAMETER`'s stated line for "enough observations to mean anything" rather than inventing a number, and the clause matters more than the value: slicing an outcome history by regime multiplies the comparisons made on it, which is the overfitting hazard `docs/TRADING_STRATEGY_REVIEW_RECORD.md` raises about this pipeline generally — a per-regime sign read off three trades would be that hazard wired into live routing. Deliberately **not** registered in `crypto_risk_limits`: that schema owns the five C4 breaker limits, which bound money loss and therefore need authorization (#356's point); a filter that only ever trades less is a different concept and one authority per concept. **The filter runs on a MATCH, not before evaluation**, so the record still shows the rules fired and says separately that the regime declined — filtering earlier would make an excluded strategy indistinguishable from one whose conditions were simply not met, and those want different responses. Same reason `regime_excluded_strategy_ids` is named on the route and `regime_excluded` on the cycle record beside `route_status`: a cycle that entered nothing because every match was regime-excluded otherwise reads identically to one where the market offered no setup. The record carries the **ids**, not a count, because a strategy excluded on every cycle for a week is a demotion candidate and a count cannot say which one; the status line prints it only when it happened, for the reason the live leg does — a field empty on almost every line trains the reader to skip it. Backward-compatible by construction and tested as such: a pool promoted before this routes byte-identically, and `run_promotion` on a candidate whose evidence predates `per_regime` installs `regime_evidence: None`. **One interaction found by merging `main`:** #359 had just landed because a SUSPENDED entry could not say why it stopped trading, and this increment creates a *new* way to stop trading that is **not a status at all** — a regime-excluded entry stays `PAPER_ACTIVE` and keeps its routing slot, so nothing in the pool says it is inert. That is the same blind spot arriving by another path, so the board counts exclusions over the cycle records it already reads, beside #359's demotion-reason line, as a **share** of cycles read: `3/12` is the filter working and `12/12` is a strategy that has stopped working here, and a bare count cannot tell those apart. **And #360, merged the same hour, asks the question this gate has to answer about itself:** it landed because the backlog counted candidates whose forward verdict was unreachable — at current rates a 1h lineage needs 29 days to reach a 20-trade window and a 1d lineage 122 — so "is there enough evidence for this rule to ever fire" is now a standing question, not a nicety. Measured rather than assumed, on a 4,000-bar mock replay across all 30 families: **15 have at least one regime slice at or above the 10-trade bar, and 13 produce at least one exclusion.** So the gate bites on roughly 43% of the library rather than being decorative — and it is reachable for the right reason, because it reads BACKTEST trades (a 12,000-bar replay) rather than live ones, which is exactly the depth #360 found live lineages lack. The families with no adequate slice are the ones that close almost nothing on the mock (htf_*, oi_* with no feeds configured, bollinger_breakout, mean_reversion), which is a mock artefact rather than a limit of the rule. The honest caveat on the same number: a hash-derived random walk makes *every* strategy lose in some regime, so this measures that the gate has evidence to act on — not that acting on it improves returns. That is a question for real replay evidence, like every other claim in this pair of increments.
- Also done: **Positioning history the runtime retains itself — collect now, decide later** (`crypto/positioning_store.py`, `crypto/market_data.py`, `crypto/cycle.py`, `crypto/dashboard.py`; 2026-07-30). Tier 2 of `docs/TRADING_ALPHA_RESEARCH_RECORD.md`, and the first increment here whose honest description is that **it makes no money today and is worth doing anyway**. Three public `/futures/data/` series of the already-authorized `binance_futures` provider — `topLongShortPositionRatio` (position bias of the top 20% of accounts by margin balance), `topLongShortAccountRatio` (the same cohort counted by account), `globalLongShortAccountRatio` (every account counted one each). **The pair is the point, not any single series:** large capital and account headcount disagreeing is a statement no column in the feature row can currently make, because every one of them would read agreement and disagreement identically. `takerlongshortRatio` is deliberately **not** collected — it restates the aggressor split the kline legs already carry, and those come with 500 days for free while this family keeps 30, so collecting it would be paying a retention wall for a worse copy of something already held. **The whole shape: it feeds nothing.** No feature reads it, no family mints against it, `snapshot` is never touched, and a test asserts that last part rather than a comment claiming it — because the day someone wires it is the day that test should turn red and make them read the docstring first. The reason is arithmetic, not caution: the endpoints keep 30 days and the factory replays 500, so a wired feature would be indeterminate over 94% of every replay window and the robustness scorer would be judging the retention wall instead of the strategy. The reason to start today rather than when a family wants the data is that **retroactive collection is impossible** — 500 days of depth is 500 days away whenever it starts, so waiting costs precisely the thing that is scarce. Progress is a field on the daily board (`포지셔닝 N/500일`), deliberately not a warning, for the reason the hourly-OI line beside it carries: a shortfall that will be true every morning for over a year is how a board teaches its reader to skip the warning block. **Two things this got wrong on the first pass and the repo caught.** (1) `attach_feeds` accumulated unconditionally, so ten existing test call sites started writing the repo's real `.runtime_governance_state/` — caught by conftest's `_tests_never_touch_the_real_state_dir` guard, which is exactly what it is for. The fix is not ten patched tests: everything else `attach_feeds` does only mutates `snapshot`, so accumulation is now **opt-in** (`accumulate=False`) and the live cycle is the single caller that turns it on. That is the `routing_marks` rule from `paper.run_paper_update` — a dry run keeps no marks because it keeps no state — and the default's failure direction is quiet rather than dangerous, since a production caller that forgot it shows as flat coverage on the board. The factory fire deliberately does **not** accumulate: one accumulator on the 15-minute cadence is what the hourly throttle is sized for, and a second would only exercise it. (2) The **trailing incomplete period must be dropped**, and this is the one bug that would have silently poisoned a 500-day accumulation from its first hour: the store dedupes on `(symbol, series, timestamp)` and is append-only, so a partial reading written now would be the value kept *forever* while the venue's later corrected reading for that same timestamp is discarded as a duplicate. Dropping it is what makes the accumulation converge on the venue's own numbers rather than on whatever it happened to see first. Everything else is `oi_store`'s shape, inherited rather than reinvented because the problem is the same one: append-only JSONL with latest-wins reads (so a re-fetch is idempotent and a gap shorter than retention self-heals), `record_sha256` per row, reads that skip damage instead of raising (the only consumer is a coverage number, and under-reporting is the safe direction), and `covered_days` measured as the oldest→newest **span** with `gap_periods` beside it, never a row count ÷ 24 that a hole in the middle would flatter. Two deliberate deltas: each series degrades **independently** and the call's overall status is the worst of the three, so one endpoint refusing neither costs the other two their readings nor reports as success; and `longShortRatio` is dropped on the way in even though the venue sends it, because it is exactly `longAccount / shortAccount` and a third stored field can disagree with the other two after rounding. **The throttle measures from the last ATTEMPT, and this branch had it wrong until `main` moved.** The first version keyed on the newest stored *reading's* age, justified in these notes as keeping one throttle shape with `oi_store` — and then #355 landed, having found that exact design never skips: the venue's newest complete period is always at least one period behind the clock (the forming one is dropped), so "the newest row is over an hour old" is true for almost every minute of every hour and all four contexts of a symbol re-ask inside one fire. The precedent this store cited changed under it, so the store followed rather than keeping a design whose own author had just fixed it: the marker is a small JSON map keyed per **(symbol, series)**, stamped **before** the request so a fetch that hangs or raises still counts, and written on failure too — a success-only marker turns a refusing endpoint into 240 asks an hour across three series and twenty contexts. Damaged marks read as *ask again*, which is fail-OPEN and the opposite of the direction this store's row reads take: a corrupt marker reading as "recently attempted" would silently stop a 500-day accumulation while the board went on reporting the coverage it already had. And whether a call seeds is a property of the **store**, not of the marks, so a machine that lost its marker file refreshes rather than re-requesting thirty days it already holds.
- Also done: **Derivative pricing and cross-asset context — the second half of the data widening** (`crypto/market_data.py`, `crypto/features.py`, `crypto/indicators.py`, `crypto/cycle.py`, `crypto/factory.py`, `scheduler.py`; 2026-07-30). Tier 1 of `docs/TRADING_ALPHA_RESEARCH_RECORD.md`, after the taker-flow entry below. Two groups, one theme: **both replaced a fabricated constant with a measurement**, which is the reason each was worth a request rather than merely nice to have. **(1) Mark / index / premium index** (`markPriceKlines`, `indexPriceKlines`, `premiumIndexKlines` — kline-shaped public endpoints of the already-authorized `binance_futures` provider, so no new provider, key or grant). `mark_price`/`index_price`/`mark_index_basis_bps` had carried the source system's documented no-feed fallbacks since C3 — `close`, `close`, and a hardcoded `0.0` — **while `factory.NUMERIC_FEATURES` admitted all three as mintable.** A literal condition on a basis that is always exactly zero does not select on anything: `basis > 0.5` could never match and `basis <= 0.5` could never fail, so the column was worse than absent, because an absent column is indeterminate and this one was confidently wrong. - Also done: **The halt peek — a `/kill` reaches the runtime before the analysis it interrupted ends** (`operator.peek_for_halt` + `PEEKABLE_HALT_VERBS`, `OperatorChannel.peek` / `TelegramChannel.peek` / `MockOperatorChannel.peek`, wired into `run_queued_task`'s stage callback; **Thomas decision K2′, 2026-07-29**, option E of `docs/proposals/CONTROL_LANE_SEPARATION_V0.1.md`). The gap was **not** "a long analysis cannot be interrupted" — it was that while one runs, `/kill` existed **nowhere in the runtime**. The operator loop is the only process that receives Telegram and it does not poll while it drains, so the control state file could not change for the length of an analysis. That file is what the crypto cycle's `live_route` re-reads immediately before a live entry, in the *other* container — which made this loop's responsiveness a dependency of the money path. The fix rides the stage boundaries the progress line already installed: at each one, read what is waiting and, if a halt is there, write the state. **The cursor is the entire risk and the entire design.** `peek` reads at the current offset with `timeout=0` and advances **nothing**, in memory or on disk: advancing would claim the whole batch while handling only the halt verb in it, silently destroying an ordinary request sent in the same second — the outcome the F1 enqueue rule exists to prevent. Because nothing is claimed, everything the peek sees arrives again at the next poll, so the peek may act only on what is safe to act on **twice**: it writes state through the same `control.apply_command` (with `ledger=None`) and never a ledger event or a reply, both of which belong to the normal handling that follows, once. `PEEKABLE_HALT_VERBS` is `{kill, pause}` and the exclusions are the safety argument, not an oversight — **`resume` is absent because a peek that could resume would let a halt be undone by a message sent *before* it, re-read out of order**; `approve` because consuming an approval twice is what `one_time_use_required` forbids; `status`/`audit` because they reply. The identity gate runs inside the peek, so an unverified `/kill` is not a shortcut into the control state. Every exception is swallowed — a safety net that can destroy the run it protects is not one — and a transport with no `peek` degrades to exactly the previous behaviour. **What this deliberately does not do: stop the running analysis.** That needs an abort path and a registry terminal for an interrupted RUNNING entry, which is decision K4 and still open; the drain already re-reads the control state before claiming the next task, so nothing further starts. Both load-bearing properties are mutation-checked: making `peek` advance the cursor, and adding `resume` to the verb set, each turn tests red. The cursor test runs against the **real** `TelegramChannel` with `_call` intercepted, because the mock cannot fail the way the real transport would.
