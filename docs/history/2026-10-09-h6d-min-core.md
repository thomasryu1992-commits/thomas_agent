# H6d-min core: exceptions get a resolution path, the ledger becomes the authority, readiness judges the present

- **Why:** Thomas approved PR-B, the H6d-min core, on 2026-10-09 (D1, D2, D4 and D5). H6b's cash-flow ledger had five
  gaps.
  - An exception had no way to be resolved, so it blocked `H6b_shadow_ready` forever.
  - The Toss evidence was a counter that only grew. One residual made the semantics MIXED for good.
  - The state file was rewritten whole without a lock. A fire and a terminal command could overwrite each other.
  - Readiness counted a source access as passing because an earlier fire had passed it.
  - Exceptions were told by a high-water count. A new exception that arrived after another was resolved went untold.
- **What this PR changes** (`holdings/cash_flows.py`, `holdings/chained_log.py`, `holdings/store.py`, one call site
  in `scheduler.py`, `scripts/holdings_board.py`):
  - **Exactly once.** `chained_log.append_unique` re-verifies the chain and drops keys the log already holds, all
    under the ledger lock. Every cash-flow append goes through it. A writer that crashes after its append and then
    reruns writes nothing twice. `chained_log.append` and the baseline log are unchanged.
  - **Locks and the authority.** Writers take the state lock, then the ledger lock, and never the reverse. Network
    reads happen outside both. The commit re-reads the ledger and the state and patches only the fields that writer
    owns.
    - The ledger is the authority for the cutover, resolutions, epochs, Toss windows, verified shadow dates and the
      first verified fire.
    - The state file keeps only caches: cursors, source health, the Toss cash point, and what has been told.
    - A missing state file is rebuilt from the ledger.
    - A state file that does not parse is refused, and so is a broken chain.
    - If the state's cutover disagrees with the ledger's, `ledger_state_consistency` fails.
    - The pre-H6d state (Toss counters, verified dates, first verified fire) is imported once as a
      `legacy_state_imported` line.
  - **Resolution.** `flow_resolved` closes the review of one open exception. Thomas runs it from his terminal; it
    needs a TTY, `--by` and `--reason`.
    - What each category may be closed as is fixed:
      - Duplicates, reversals, malformed rows and other holds: `acknowledged_excluded` only.
      - A payment: the direction the venue gave.
      - A Toss residual: deposit or income if positive, withdrawal or fee if negative, `semantics_mismatch`, or
        `read_incomplete` (truncated reads only).
    - These are refused: an unknown target, a target that is not an exception, a second resolution, an applied
      event, and a pre-cutover event.
    - The event stays HELD. `lifecycle` keeps three judgements apart: review closure, evidence validation and
      accounting eligibility. In H6b the last two are never true.
  - **Toss windows.** Each fire writes a `toss_window_observed` line. It carries the window, the epoch, the
    reconciliation fingerprint, order hashes for buys, sells and settlements, the residual status per pocket,
    truncation and exchange flags, and the order query.
    - Evidence is recomputed from these lines per epoch:
      - Buys and sells count only from explained, untruncated, unamended windows with stable order identity, and
        each order counts once.
      - A settlement day needs at least 12 windows and nothing spoiled that day.
      - A window closed as an external flow is never trade evidence.
      - MIXED recovers only on evidence gathered after the problem window.
    - Order identity is a set of hashes: the venue's id, and side + currency + order time + symbol. Two reads that
      share a hash are one order. An order with neither hash is `unstable`, and its window is no evidence.
  - **Late evidence.** A `toss_window_amended` line records late evidence, keyed and idempotent:
    `late_fill`, `settlement_revised` or `identity_unstable`.
    - An amendment only withdraws evidence.
    - A late fill in a window that was explained is a contradiction, which makes it MIXED.
  - **Epochs.** `toss_semantics_epoch_started` is started by Thomas at his terminal. It needs a TTY, `--by`,
    `--reason`, a `--change-ref` (`#PR` or a commit), and the first 8 characters of the reconciliation digest typed
    back.
    - The digest is the hashed output of the reconciliation over fixed synthetic cases. It must differ from the last
      epoch's, so a code change with the same output is refused. The AST fingerprint is recorded alongside as
      support.
    - The first epoch is the one-time transition from the pre-H6d counters.
    - Earlier lines, their MIXED and every open exception stay as they are. A new epoch starts WAITING.
  - **Cutover.** One rule, `event_phase`:
    - Binance uses the venue's `event_ms`.
    - A Toss window is PRE or POST only when it lies wholly on one side of the cutover. A window that straddles it
      is UNKNOWN, and still blocks.
    - A malformed row uses the time it was first seen.
    - Migration rules are unchanged. Shadow dates belong to a cutover generation, so moving back revives none.
  - **Current health.** `readiness(..., current=)` takes this fire's results: every history read, the Toss pass,
    and the combined NAV's freshness and coherence. Without them, the access, schema, transfer and health checks
    are `UNCHECKED`. A source skipped for the read budget is no longer reported as PASS.
  - **Notification.** Each open exception is told once, by key digest.
    - The untold set is pinned under a token, and the scheduler hands the token back only after delivery.
    - A message still in flight never marks an exception found after it was built.
    - The H6b `told_count` carries over without repeating a message.
    - Messages carry counts only.
  - **Terminal.** `--flows` lists exceptions with their key, category, phase, review state and allowed kinds. It
    prints no amounts. `--resolve` and `--semantics-epoch` are the two writes. PR-A's guard already refuses all
    three for Claude.
- **Tests.** Four new files with 75 cases cover the 44 scenarios plus order identity, cutover, the CLI and the
  notification edges. The concurrent cases run in real processes: refresh against resolve, two resolves, a crash
  after the append, and a stale cache. Fourteen mutations were each caught.
  - Eight cases are POSIX-only: six fork processes and two run the bash guard. `tests/skip_ceiling.json` takes
    win32 from 206 to 214. 214 is the count the PR's Windows CI read on top of main `11de0e94` (#1203).
- **Existing tests changed, with the contract that moved:**
  - Toss tests filter out the new per-fire window line and assert its status.
  - Evidence reads come from the ledger, not from a state counter.
  - Readiness tests pass the fire's health; the tests also assert `UNCHECKED` without it.
  - Shadow dates are read from the ledger, and moving the cutover back revives nothing.
  - Exception telling uses the token.
  - Fixture orders carry an id.
  No assertion was dropped.
- **What it does not do:**
  - No 72-hour maturity, 7-day seal, deep historical scan, new read cadence or health threshold: these wait on
    separate approval.
  - No unit, no NAV per unit, no H6c. Nothing turns on by itself.
  - The accounting mode stays shadow. No trading permission changes.
  - Claude runs none of the terminal modes on real data.
